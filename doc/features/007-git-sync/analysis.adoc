== Видение

Проблема::
Инженер в docs-as-code процессе правит документацию в дороге, но довести правку до команды не может: цикл заканчивается на телефоне, потому что commit и push требуют ноутбука.
Обходные пути — синхронизация сторонним клиентом или копирование файлов — рвут связь с историей и code review.

Для кого::
*Инженер* — единственная роль этой фичи: работает в репозитории (Git + AsciiDoc + CI), правит и коммитит с телефона.
Автору заметок без Git фича не мешает: приложение работает с обычными папками, как раньше.

Желаемый результат::
Полный цикл на устройстве: склонировать репозиторий, увидеть состояние ветки и файлов, забрать чужие правки, выбрать файлы, закоммитить и отправить — включая простое разрешение конфликта.
Проверяемо историями xref:../../user-stories.adoc#US-E5-01[US-E5-01]…xref:../../user-stories.adoc#US-E5-05[US-E5-05] и xref:../../user-stories.adoc#US-E1-04[US-E1-04].

Не-цели::
+
--
* *Не merge-редактор.* Конфликт решается выбором «локальное / удалённое / оба» по участкам — решение видения, построчное слияние осознанно за бортом.
* *Не Git-клиент общего назначения.* Ни истории веток, ни rebase, ни cherry-pick, ни управления ветками: одна ветка, выбранная при клоне.
История файла (`US-E5-06`, `T-114`) — отдельная задача следующей итерации.
* *Не iOS в этой фиче.* Интерфейс проектируется на обе платформы, реализуется Android (xref:../../adr/adr-002-android-first.adoc[ADR-002]).
* *Не фоновая синхронизация.* Никаких воркеров и расписаний, пока авто-fetch не решён (OQ-5): все операции запускает пользователь.
--

Ценность и почему сейчас::
Это подтверждённая фича продукта из видения и самая длинная цепочка плана после MVP (`T-070` → `T-071` → экраны), поэтому начинать её нужно первой из построек после шлюза.
Она же впервые делает содержательными НФТ «секреты» и «офлайн».

[NOTE]

=== Функциональные: интерфейс синхронизации

FR-1 (M)::
Интерфейс синхронизации ДОЛЖЕН жить в `commonMain` и не раскрывать типов JGit: модели статуса, прогресса, конфликта и ошибок — платформенно-нейтральные.
Платформенная реализация подключается фабрикой, независимо для каждой платформы (`T-070`).

FR-2 (M)::
На платформе без реализации Git-возможности ДОЛЖНЫ быть выключены целиком (разделы UI не показываются), а не падать: Android может выйти с Git раньше iOS — решение видения.

=== Функциональные: клонирование (`US-E5-01`, макет 05)

FR-3 (M)::
Форма клонирования ДОЛЖНА принимать URL, способ авторизации (`SSH-КЛЮЧ` / `ТОКЕН` / `БЕЗ АВТ.` сегментированным переключателем), ветку и целевую папку.

FR-4 (M)::
Опция поверхностного клона `depth 1` ДОЛЖНА быть доступна на форме.
Основание объёма: разведка — память JGit ограничена мобильной кучей, `depth 1` — главная митигация.

FR-5 (M)::
Во время клонирования ДОЛЖЕН показываться прогресс: процент, число объектов, скорость — чертёжным блоком по макету 05.

FR-6 (M)::
Клон ДОЛЖЕН помещаться в хранилище с прямым файловым доступом (`java.io.File`): SAF-дерево для JGit непригодно — факт разведки.
Конкретное место хранения и видимость файлов другим приложениям — OQ-1; до решения формулировка «другие приложения видят те же файлы» из `US-E5-01` считается неподтверждённой.

FR-7 (M)::
Ошибка клонирования (неверный URL, нет сети, отказ авторизации) ДОЛЖНА показываться понятным сообщением, а частичный клон — не оставаться на диске под видом целого.

FR-8 (M)::
Склонированный репозиторий ДОЛЖЕН открываться после перезапуска приложения без повторного клонирования.

=== Функциональные: состояние репозитория (`US-E5-02`, `US-E1-04`, макет 01)

FR-9 (M)::
Экран репозитория ДОЛЖЕН показывать карточку ветки: имя, счётчики `↓N ↑N`, число локальных изменений, адрес remote.

FR-10 (M)::
Список файлов ДОЛЖЕН показывать метку статуса (`M`, `A`, `?`), путь, время последней правки и фильтры `ИЗМЕНЁННЫЕ` / `ВСЕ ФАЙЛЫ` / `НЕДАВНИЕ`; для папки — число вложенных файлов.

FR-11 (M)::
Счётчики карточки ДОЛЖНЫ обновляться после pull и после commit.
Счётчик `↓N` честен только после fetch; когда fetch выполняется — OQ-5, до решения счётчик считается по последнему известному состоянию origin.

FR-12 (M)::
Файл из списка ДОЛЖЕН открываться в существующем редакторе; правка и автосохранение работают как для обычного файла.

=== Функциональные: pull (`US-E5-03`)

FR-13 (M)::
Pull ДОЛЖЕН запускаться одной кнопкой с экрана репозитория.

FR-14 (M)::
Результат ДОЛЖЕН сообщаться явно: обновлено, уже актуально или конфликт.

FR-15 (M)::
Открытый в редакторе файл, изменённый pull-ом, ДОЛЖЕН перечитываться; несохранённые локальные правки при этом НЕ ДОЛЖНЫ теряться.
Механизм (блокировать pull до сохранения, сохранять перед pull или сливать в буфере) — OQ-4.

FR-16 (M)::
Pull без сети ДОЛЖЕН завершаться понятной ошибкой, не меняя состояния репозитория.

=== Функциональные: commit и push (`US-E5-04`, макет 03)

FR-17 (M)::
Экран коммита ДОЛЖЕН показывать индекс с чекбоксами, меткой статуса и дифф-счётчиками `+41 −6`; в коммит попадают только отмеченные файлы.

FR-18 (M)::
Неотслеживаемые файлы по умолчанию НЕ ДОЛЖНЫ быть включены в индекс.

FR-19 (M)::
Счётчик символов ДОЛЖЕН подсказывать длину первой строки сообщения (`50 / 72 симв.`); ввод сообщения длиннее НЕ блокируется.

FR-20 (M)::
Переключатель «Отправить в origin после коммита» ДОЛЖЕН объединять commit и push в одно действие.

FR-21 (M)::
Отказ push (нет сети, нет прав, non-fast-forward) НЕ ДОЛЖЕН откатывать уже сделанный локальный коммит и ДОЛЖЕН сообщаться отдельно от результата коммита.

FR-22 (M)::
Авторство коммита (`user.name`, `user.email`) ДОЛЖНО быть задано до первого коммита; где и как оно вводится — OQ-8.

=== Функциональные: конфликт (`US-E5-05`, макет 04)

FR-23 (M)::
Для каждого конфликтного участка ДОЛЖНЫ показываться локальная и удалённая версии с автором и временем, варианты `ЛОКАЛЬНОЕ` / `УДАЛЁННОЕ` / `ОБА` и предпросмотр результата, пересобираемый сразу при выборе.

FR-24 (M)::
Счётчик `1/2` ДОЛЖЕН показывать прогресс по участкам; завершить слияние МОЖНО только после разрешения всех участков.

FR-25 (M)::
До завершения слияния ДОЛЖНА быть доступна отмена: репозиторий возвращается в состояние до pull, локальные коммиты не теряются.

=== Функциональные: авторизация и секреты

FR-26 (M)::
Клонирование и последующие сетевые операции ДОЛЖНЫ работать по HTTPS с токеном: токен вводится один раз и переиспользуется для fetch, pull и push этого репозитория.

FR-27 (M)::
Клонирование и последующие сетевые операции ДОЛЖНЫ работать по SSH с приватным ключом; выбранный ключ подписан в переключателе авторизации (макет 05).
Откуда берётся ключ (генерация или импорт) — OQ-3.

FR-28 (M)::
Секреты (токен, приватный ключ) ДОЛЖНЫ храниться в платформенном защищённом хранилище, НЕ ДОЛЖНЫ лежать в настройках приложения и НЕ ДОЛЖНЫ попадать в логи (`T-072`).
Конкретная схема хранения — OQ-2.

FR-29 (S)::
При первом SSH-соединении с неизвестным или сменившимся host key приложение ДОЛЖНО спросить подтверждение у пользователя; молча доверять нельзя.
Основание: прецедент orgzly в разведке.

FR-30 (C)::
URL с встроенными учётными данными (`https://user:token@…`) МОЖЕТ отвергаться с подсказкой использовать поле авторизации: секрет в URL попадает в конфиг репозитория открытым текстом.

=== Нефункциональные

[IMPORTANT]
Чеклист проектный (xref:../../development-rules.adoc[правила разработки]); по каждой строке — требование или «неприменимо».

[cols="1,1,3", options="header"]
|===
| ID | Категория | Требование или решение

| NFR-1
| Отзывчивость
| Git-операции выполняются вне главного потока; ввод и прокрутка не замирают во время операции.
Длительные операции (clone, pull, push) показывают прогресс или явное состояние «идёт»; числовых порогов длительности не ставим — они зависят от сети и размера репозитория.

| NFR-2
| Доля общего кода
| Интерфейс, модели, логика экранов и разбор конфликтных участков — `commonMain`; в платформе только JGit-реализация интерфейса и хранилище секретов.
Шов — интерфейс с платформенной фабрикой, а не `expect`/`actual`-функции; так iOS подключается независимо (решение видения, не новая развилка).

| NFR-3
| Офлайн
| Всё локальное (статусы, commit, разрешение конфликта, чтение файлов) работает без сети.
В сеть выходят только clone, fetch, pull и push — по явному действию пользователя; их отказ без сети — штатное сообщение, состояние репозитория не портится.
Очередь отложенных push — OQ-6, до решения очереди нет.

| NFR-4
| Паритет платформ
| iOS отстаёт осознанно: интерфейс общий, реализация Android-first (xref:../../adr/adr-002-android-first.adoc[ADR-002], решение видения).
Это записанное решение, а не умолчание.

| NFR-5
| Жизненный цикл
| Убийство процесса посреди операции — штатный сценарий: незавершённый клон не выдаётся за целый (FR-7), stale-lock (`.git/index.lock`) обнаруживается и снимается с подтверждением, а не роняет все последующие операции.
Уход в фон не отменяет начатый push/pull, пока система не убила процесс.

| NFR-6
| Файлы пользователя
| Рабочая копия — обычные файлы; приложение не меняет их кодировку и переводы строк сверх того, что делает существующий document-слой (фича 004).
Автопреобразование переводов строк Git-ом не включаем: `core.autocrlf` остаётся выключенным, чтобы файл на диске совпадал с тем, что коммитится.

| NFR-7
| Ввод и клавиатура
| Применимо только полям форм (URL, сообщение коммита): обычное поведение IME, поле сообщения не уходит под клавиатуру (`WindowInsets.ime`).
Остальное — неприменимо.

| NFR-8
| Безопасность и данные
| Первая фича, где строка содержательна: токен и ключ — только в защищённом хранилище (FR-28); в логи запрещено писать секреты, URL с кредами и содержимое ключей; наружу уходят только Git-протокольные обмены с указанным remote по TLS/SSH.
`security-review` обязателен в ревью каждого слайса, касающегося секретов и сети (xref:../../development-rules.adoc[правила]).

| NFR-9
| Доступность
| Статусы файлов — буквами (`M`, `A`, `?`), не только цветом; выбранный вариант конфликта — рамка плюс фон (двойное кодирование из дизайна); счётчики и прогресс — текстом с числами.

| NFR-10
| Тестируемость
| Логика экранов и модели — `commonTest` с фейковой реализацией интерфейса синхронизации.
JGit-цикл — инструментальные тесты на устройстве против локального `file://`-remote, без сети: сеть и авторизация недетерминированы, поэтому HTTPS/SSH против настоящего сервера — ручные кейсы.
|===

=== Ограничения и допущения

Ограничения::
* Решения видения: JGit на Android; libgit2 на iOS позже; конфликт — «mine / theirs», не merge-редактор; Git — итерация после MVP.
* `minSdk 26` — пол JGit и MINA sshd на Android (разведка); уже совпадает с проектным.
* JGit ≥ 7.0 требует Java 17 — совместимо с JDK 21 проекта.
* Клон живёт только в хранилище с прямым File-доступом (разведка, Q4).

Допущения::
* Стоковый JGit 7.x работает на ART — гипотеза H1 разведки, проверяется спайком до реализации; при провале — откат на линию 6.x (Java 11) с тем же API.
* Push из shallow-клона проходит против типовых серверов — гипотеза H2, тот же спайк.
* Репозитории — документационные (десятки мегабайт), не монорепо; пороги размера не заявляем.

Зависимости::
* Новые библиотеки: `org.eclipse.jgit`, `org.eclipse.jgit.ssh.apache` (версии — в каталог `gradle/libs.versions.toml`).
* Фичи 004 (document-слой) и 005 (экран редактора) — открытие файла клона в редакторе.
* Тестовый Git-сервер для ручных кейсов HTTPS/SSH.

== Интеграция в приложение

Поверхности::
Четыре новых экрана: репозиторий (01), клонирование (05), commit/push (03), конфликт (04); экран репозитория становится корнем навигации (xref:../../adr/adr-003-layout-1a.adoc[ADR-003]).
Существующий экран редактора получает вход «файл из репозитория».

Общий код::
`git/` в `commonMain`: интерфейс синхронизации, модели (статус репозитория, статус файла, прогресс, участок конфликта, ошибки), разбор конфликтных маркеров, логика сборки результата «mine/theirs/оба»; `screen/git/` — модели четырёх экранов.

Платформенные адаптеры::
`androidMain`: реализация интерфейса на JGit + MINA sshd; хранилище секретов на Android Keystore; File-реализация доступа к файлам клона для document-слоя.
Это третий платформенный шов после рендера и превью — предусмотрен видением, в ≤ 20 % платформенного кода закладывается заранее.

Состояние и корутины::
Модель экрана владеет состоянием (образец — `EditorScreenModel`); Git-операции — `suspend` на IO-диспетчере; одна операция за раз на репозиторий, повторный запуск блокируется состоянием, а не гонкой.

Настройки::
Авторство коммита и параметры авторизации — кандидаты в настройки (OQ-8, OQ-2); в группе настроек из макета 06 раздела Git пока нет — дизайну потребуется дополнение.

== Сценарии использования

=== UC-1 — клонировать репозиторий

Актор:: инженер · *Тип триггера:* `user` · *Уровень:* user-goal
Триггер, предусловия, постусловия:: открыт экран клонирования; после — репозиторий на устройстве, экран репозитория показывает его состояние.
Основной сценарий:: . Инженер вводит URL, выбирает способ авторизации, ветку, папку и `depth 1`. . Нажимает `КЛОНИРОВАТЬ`. . Видит прогресс (процент, объекты, скорость). . По завершении попадает на экран репозитория.
Расширения:: 2a. `ТОКЕН` → токен запрашивается и сохраняется в защищённое хранилище. 2b. `SSH-КЛЮЧ` → используется сохранённый ключ; неизвестный host key → подтверждение (FR-29). *a. Ошибка сети/URL/авторизации → сообщение, частичного клона не остаётся (FR-7).
Покрывает:: FR-3…FR-8, FR-26, FR-27, FR-29.

=== UC-2 — посмотреть состояние и открыть файл

Актор:: инженер · *Тип триггера:* `user` · *Уровень:* user-goal
Основной сценарий:: . Открывает экран репозитория. . Видит карточку ветки и список файлов со статусами. . Фильтрует (`ИЗМЕНЁННЫЕ`). . Открывает файл — редактор работает как обычно.
Расширения:: 2a. Изменений нет → счётчик изменений `0`, список в фильтре «изменённые» пуст.
Покрывает:: FR-9…FR-12.

=== UC-3 — pull без конфликта

Актор:: инженер · *Тип триггера:* `user` · *Уровень:* user-goal
Основной сценарий:: . Нажимает `PULL`. . Видит явный результат: обновлено или уже актуально. . Счётчики карточки обновляются. . Открытый файл, изменённый pull-ом, перечитан; несохранённые правки не потеряны.
Расширения:: *a. Нет сети → сообщение, состояние не тронуто (FR-16). 2a. Конфликт → UC-5.
Покрывает:: FR-11, FR-13…FR-16.

=== UC-4 — commit и push

Актор:: инженер · *Тип триггера:* `user` · *Уровень:* user-goal
Основной сценарий:: . Открывает экран коммита. . Снимает и ставит чекбоксы; неотслеживаемый файл по умолчанию снят. . Пишет сообщение, следя за счётчиком `50 / 72`. . Включает «отправить в origin» и подтверждает. . Коммит создан, push прошёл, счётчик `↑` обнулился.
Расширения:: 5a. Отказ push (сеть, права, non-fast-forward) → коммит на месте, отдельное сообщение об отказе (FR-21). 3a. Авторство не задано → запрос имени и почты до коммита (FR-22).
Покрывает:: FR-17…FR-22.

=== UC-5 — разрешить конфликт

Актор:: инженер · *Тип триггера:* `user` · *Уровень:* user-goal
Триггер, предусловия, постусловия:: pull завершился конфликтом; после — слияние завершено либо отменено, репозиторий в согласованном состоянии.
Основной сценарий:: . Экран конфликта показывает участок: локальная и удалённая версии, авторы, время. . Инженер выбирает `ЛОКАЛЬНОЕ` / `УДАЛЁННОЕ` / `ОБА`; блок результата пересобирается. . Переходит `ДАЛЕЕ` по счётчику `1/2`. . После последнего участка завершает слияние.
Расширения:: 4a. Не все участки разрешены → завершение недоступно (FR-24). *a. Отмена → состояние до pull, коммиты целы (FR-25).
Покрывает:: FR-23…FR-25.

=== UC-6 — процесс убит во время операции

Актор:: система (Android) · *Тип триггера:* `system-event` · *Уровень:* subfunction
Основной сценарий:: . Система выгружает процесс посреди клона или pull. . При следующем запуске приложение обнаруживает незавершённое состояние. . Незавершённый клон не выдаётся за целый; stale-lock снимается с подтверждением; операция повторяема.
Покрывает:: NFR-5, FR-7.

== Тест-кейсы

[NOTE]
Automatable-кейсы уровня логики — `commonTest` на фейковой реализации интерфейса; кейсы с пометкой `device` — инструментальные, JGit против локального `file://`-remote на устройстве; `manual` — против настоящего сервера или руками.
Имя теста начинается с идентификатора (`TC_1_…`) — по нему сверка находит покрытие.

=== Клонирование

TC-1 (happy, device):: Клон публичного `file://`-remote создаёт рабочую копию: файлы на диске совпадают с содержимым remote, экранная модель получает событие завершения.
TC-2 (happy, device):: Клон с `depth 1` оставляет в истории один коммит: `log` по HEAD насчитывает ровно 1.
TC-3 (happy, automatable):: События прогресса (процент, объекты, скорость) доходят до модели экрана в порядке возрастания и завершаются терминальным состоянием.
TC-4 (negative, automatable):: Ошибка клонирования переводит модель в состояние ошибки с человекочитаемым сообщением; повторный запуск возможен.
TC-5 (negative, device):: Прерванный клон не оставляет каталога, который приложение считает валидным репозиторием: повторное открытие предлагает клонировать заново.
TC-6 (happy, device):: Склонированный репозиторий открывается после перезапуска процесса без сети (FR-8).

=== Состояние репозитория

TC-7 (happy, device):: Изменённый, добавленный и неотслеживаемый файлы получают метки `M`, `A`, `?` соответственно.
TC-8 (happy, automatable):: Фильтр `ИЗМЕНЁННЫЕ` оставляет только файлы с не-чистым статусом; `ВСЕ ФАЙЛЫ` возвращает полный список.
TC-9 (happy, device):: Локальный коммит увеличивает `↑` на 1; pull, забравший чужой коммит, обнуляет `↓` (FR-11).
TC-10 (happy, automatable):: Карточка ветки отдаёт имя ветки и адрес remote в модели экрана — значения совпадают с заданными при клоне.

=== Pull

TC-11 (happy, device):: Pull при отставании от origin обновляет рабочую копию и сообщает «обновлено»; содержимое файла после pull совпадает с версией remote.
TC-12 (edge, device):: Pull без расхождений сообщает «уже актуально» и не создаёт коммитов.
TC-13 (edge, automatable):: Файл, открытый в редакторе и изменённый pull-ом, перечитывается; несохранённый текст пользователя не теряется (механизм — по решению OQ-4; кейс уточняется вместе с ним).
TC-14 (negative, device):: Pull при недоступном remote завершается ошибкой; `status` до и после идентичен.

=== Commit и push

TC-15 (happy, device):: В коммит попадают только отмеченные файлы: снятый файл остаётся изменённым после коммита.
TC-16 (happy, automatable):: Неотслеживаемый файл приходит в модель экрана со снятым чекбоксом (FR-18).
TC-17 (happy, automatable):: Счётчик символов считает длину первой строки сообщения и не блокирует ввод сверх 72.
TC-18 (happy, device):: «Commit & push» одним действием создаёт коммит и доводит его до remote: `log` remote содержит новый коммит.
TC-19 (negative, device):: Push при недоступном remote или non-fast-forward оставляет локальный коммит на месте; модель сообщает отказ push отдельно от успеха коммита (FR-21).
TC-20 (happy, device):: Коммит несёт заданные `user.name` и `user.email`.

=== Конфликт

TC-21 (happy, device):: Конфликтный pull переводит модель в состояние конфликта со списком участков; счётчик показывает `1/N`.
TC-22 (happy, automatable):: Выбор `ЛОКАЛЬНОЕ` собирает результат из локальной версии участка; `УДАЛЁННОЕ` — из удалённой; `ОБА` — обе версии в порядке «локальная, затем удалённая».
TC-23 (happy, automatable):: Предпросмотр результата пересобирается сразу при смене выбора.
TC-24 (negative, automatable):: Завершение слияния недоступно, пока хотя бы один участок не разрешён (FR-24).
TC-25 (happy, device):: После разрешения всех участков слияние завершается merge-коммитом; `status` чист, маркеров конфликта в файле нет.
TC-26 (edge, device):: Отмена слияния возвращает репозиторий в состояние до pull; локальные коммиты целы (FR-25).

=== Авторизация и секреты

TC-27 (happy, manual):: Клон приватного репозитория по HTTPS с токеном проходит; повторный push не запрашивает токен заново (FR-26).
TC-28 (happy, manual):: Клон по SSH с сохранённым ключом проходит; подпись ключа видна в переключателе (FR-27).
TC-29 (negative, manual):: Неизвестный host key останавливает соединение до подтверждения пользователем (FR-29).
TC-30 (happy, device):: Токен, сохранённый хранилищем секретов, отсутствует в файлах настроек приложения (побайтовый поиск по каталогу данных) и переживает перезапуск процесса (FR-28).
TC-31 (negative, automatable):: Строки логов, порождаемые Git-слоем на операциях с авторизацией, не содержат токена, ключа и URL с кредами (FR-28, NFR-8).

=== Жизненный цикл и потоки

TC-32 (edge, device):: Убийство процесса посреди операции, затем перезапуск: stale-lock обнаружен, снимается предложенным действием, следующая операция проходит (NFR-5).
TC-33 (happy, device):: Git-операции не исполняются на главном потоке: проверка потока внутри фейкового наблюдателя операции (NFR-1).

== Технический подход

[NOTE]
Якоря, сужающие «как», а не полный дизайн. Гипотезы, не жёсткий контракт.

Паттерны для подражания::
Тонкий шов с платформенной реализацией — `document/DocumentFileAccess.kt` и `DocumentTreeAccess.kt` (фича 004); модель экрана на корутинах — `screen/EditorScreenModel.kt`; чертёжные блоки — `ui/AdocBlueprintBlock.kt`; device-тесты — `androidDeviceTest` фичи 003.

Точки интеграции::
Экран репозитория — корень навигации (ADR-003); открытие файла клона — через File-реализацию доступа document-слоя, минуя SAF; счётчик изменений на кнопке `COMMIT · 3` — из статуса репозитория.

Предполагаемые артефакты::
`commonMain`: `git/GitSync.kt` (интерфейс + модели), `git/ConflictHunks.kt` (разбор маркеров, сборка результата), `screen/git/*ScreenModel.kt` и экраны; `commonTest`: фейк `FakeGitSync` + тесты моделей; `androidMain`: `git/JGitSync.kt`, `git/SecretStore.kt`; `androidDeviceTest`: цикл против `file://`-remote; каталог версий — координаты JGit и sshd.

Явные рамки и запреты::
Типы JGit не пересекают границу `commonMain`; секреты не попадают в `SharedPreferences`, файлы настроек и логи; никакого фонового исполнения операций; конфликт первой версии — только «локальное / удалённое / оба»; iOS-реализация не пишется, но интерфейс не должен опираться на JVM-типы.

Связанные ADR::

== Решённые вопросы

*OQ-1 — куда кладётся клон.*
Решено владельцем 2026-08-17: клон живёт в приватном `filesDir` (JGit работает с обычными файлами без компромиссов), а видимость другим приложениям обеспечивает *собственный `DocumentsProvider`* — репозиторий доступен через системный выбор файлов.
Критерий `US-E5-01` выполнен; провайдер — отдельный компонент и может ехать вторым этапом фичи, не блокируя клонирование и синхронизацию.

== Открытые вопросы

Развилки записаны с вариантами и ценой; ни одна не решена этим документом — все требуют решения владельца.

* [ ] *OQ-1. Куда кладётся клон — и что делать с критерием `US-E5-01` «другие приложения видят те же файлы».*
JGit требует прямого File-доступа (разведка, Q4), поэтому SAF-папка пользователя невозможна в принципе — но каждый вариант с File-доступом чем-то платит:
(а) приватное хранилище приложения (`filesDir`) — просто и надёжно, но файлы не видны другим приложениям: критерий истории придётся ослабить правкой `US-E5-01`;
(б) app-specific внешний каталог (`Android/data/…`) — то же самое с Android 11, выигрыша нет;
(в) полный доступ к общему хранилищу (`MANAGE_EXTERNAL_STORAGE`) — файлы видны всем, но разрешение конфликтует с политикой Google Play;
(г) приватное хранилище плюс собственный `DocumentsProvider` — другие приложения видят файлы через системный выбор документов, критерий формально выполняется, цена — отдельный компонент и его сопровождение.
Решение меняет формулировку `US-E5-01`, поэтому оно — до начала реализации.
* [ ] *OQ-2. Схема хранения секретов.*
`EncryptedSharedPreferences` deprecated (разведка, Q5).
Варианты: (а) файл, шифрованный AES-ключом из Android Keystore, — минимум зависимостей, свой код шифрования; (б) DataStore + Tink с ключом в Keystore — рекомендованное направление, плюс две зависимости; (в) остаться на deprecated API — не вариант, только как осознанный долг.
* [ ] *OQ-3. SSH-ключ: генерация в приложении, импорт или оба.*
Генерация (ed25519) безопаснее — приватный ключ не покидает устройство, но требует UI показа публичного ключа для регистрации на сервере.
Импорт (вставка/файл) быстрее для существующих ключей, но проводит приватный ключ через буфер обмена или хранилище.
Гипотеза H4 разведки (Keystore не подписывает ed25519) влияет на обе ветки.
* [ ] *OQ-4. Pull при несохранённых правках открытого файла.*
Варианты: (а) сохранить автосохранением перед pull — просто, но правка попадает в pull и может стать конфликтом; (б) блокировать pull до сохранения — честно, но лишний шаг; (в) перечитать файл и слить несохранённый буфер поверх — лучший UX, самая дорогая и рискованная логика.
`US-E5-03` требует лишь «не терять правки» — механизм открыт.
* [ ] *OQ-5. Fetch: по расписанию, при входе на экран или только вручную.*
Без fetch счётчик `↓N` устаревший.
Варианты: (а) только вручную (pull) — честно оффлайн, счётчик живёт от последнего pull; (б) fetch при открытии экрана репозитория — свежие счётчики, неожиданный сетевой трафик; (в) фоновое расписание — максимум свежести, ломает «не-цель» фоновой синхронизации и жрёт батарею.
* [ ] *OQ-6. Push без сети: ошибка сразу или очередь на повтор.*
Очередь удобнее в дороге, но требует состояния «ожидает отправки», её отмены и поведения при смене ветки; ошибка сразу — проще и предсказуемее, коммит и так не теряется.
* [ ] *OQ-7. Один репозиторий или несколько.*
Макеты показывают один; несколько — это реестр, выбор активного и умножение состояний.
Дешёвый компромисс: хранить один, но не зашивать единственность в модель.
* [ ] *OQ-8. Где вводится авторство коммита (`user.name` / `user.email`).*
В макете 06 группы Git нет.
Варианты: (а) запрос при первом коммите; (б) новая группа в настройках; (в) шаг формы клонирования.
Требует дополнения дизайна — вопрос и к владельцу, и к макетам.
