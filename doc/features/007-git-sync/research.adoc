== Как решает эталон

Эталон здесь двухслойный: нативный `git` задаёт контракт поведения, а мобильные приложения с JGit показывают, что из него реально переносится на Android.

[cols="1,2,2,2", options="header"]
|===
| Что | Где (класс, файл, документ) | Как устроено | Что берём

| Полный цикл API
| `org.eclipse.jgit.api.Git`: `CloneCommand`, `PullCommand`, `AddCommand`, `CommitCommand`, `PushCommand`, `StatusCommand` — https://github.com/eclipse-jgit/jgit/wiki/User-Guide[JGit User Guide]
| Porcelain-API поверх `Repository`; всё работает на `java.io.File`, не на URI
| Весь цикл фичи ложится на porcelain-API; свой транспортный код не пишем

| SSH-транспорт на Android
| https://github.com/orgzly/orgzly-android/pull/948[orgzly-android PR #948] (заменён https://github.com/orgzly/orgzly-android/issues/904[#1037], вмержен 2023)
| JGit + `org.eclipse.jgit.ssh.apache` (Apache MINA sshd); требование API ≥ 26; `known_hosts` — в приватной директории `.ssh` приложения; при новом или сменившемся host key нужен собственный UI подтверждения
| Прецедент, что MINA sshd работает на Android; паттерн хранения `known_hosts`; необходимость экрана подтверждения host key

| Авторизация HTTPS-токеном
| https://www.codeaffine.com/2014/12/09/jgit-authentication/[JGit Authentication Explained], https://medium.com/autotrader-engineering/working-with-git-in-java-part-1-a-jgit-tutorial-bc03b404a517[JGit tutorial (Autotrader)]
| `TransportCommand.setCredentialsProvider(new UsernamePasswordCredentialsProvider(token, ""))` — PAT передаётся как имя пользователя с пустым паролем; работает для clone, fetch, pull, push
| Механизм целиком; токен в URL не встраиваем

| Разрешение конфликта «mine / theirs»
| Контракт `git checkout --ours/--theirs` и маркеры конфликта в файле; выбор варианта — решение видения (xref:../../asciidoc-editor-vision.adoc[видение], раздел «Следующие итерации»)
| После неуспешного merge JGit оставляет маркеры и стадии в индексе (`Status.getConflicting()`)
| Участки конфликта читаем из маркеров файла; построчный merge-редактор не делаем
|===

== Что даёт платформа

|===

| `org.eclipse.jgit:org.eclipse.jgit`
| 7.7.1.202607240634-r (июль 2026, https://javadoc.io/doc/org.eclipse.jgit/org.eclipse.jgit/latest/index.html[javadoc.io])
| Полный Git-цикл на чистой Java

| `org.eclipse.jgit.ssh.apache` (Apache MINA sshd)

| с 6.3 (https://wiki.eclipse.org/JGit/New_and_Noteworthy/6.3[New and Noteworthy 6.3])
| `CloneCommand`/`FetchCommand`: `setDepth` (`--depth`), `setShallowSince`, `addShallowExclude`
| Статьи до 2022 года («JGit не умеет shallow») устарели. Поведение push из shallow-клона JGit публично не документировано — гипотеза ниже

| Защищённое хранилище секретов
| `androidx.security:security-crypto` 1.1.0-alpha07 — все API объявлены deprecated (https://developer.android.com/jetpack/androidx/releases/security[журнал релизов Jetpack Security])
| —
| `EncryptedSharedPreferences` больше не рекомендован; официальное направление — платформенные API и прямое использование Android Keystore; типовой паттерн миграции — DataStore + Tink + Keystore (https://www.droidcon.com/2025/12/16/goodbye-encryptedsharedpreferences-a-2026-migration-guide/[обзор droidcon, 2025])

| libgit2 (для будущего iOS)
| shallow clone поддержан с 1.7.0 (https://github.com/libgit2/libgit2/discussions/6595[анонс v1.7.0])
| Полный цикл на C, C-interop из Kotlin/Native

Гипотезы::
+
--
* *H1 — подтверждена спайком E0.* Стоковый JGit 7.7.x запускается на ART без модификаций при `minSdk 26`.
Проверено фактом: shallow clone этого же репозитория по HTTPS с устройства за ~2,2 с — <<spike-e0-h1>>.
Оговорка сборки: конвейер дексации device-тестов KMP-модуля JGit 7.x не пропускает — <<spike-e0-build>>.
* *H2 — подтверждена спайком E0 (для `file://`).* Push из shallow-клона `depth 1` через JGit проходит.
Нативный git это допускает, серверные оговорки касаются `receive.shallowUpdate` (https://gitlab.com/gitlab-org/gitlab-foss/-/issues/3033[обсуждение GitLab]).
Клиентская сторона JGit проверена фактом против `file://`-remote — <<spike-e0-h2>>; поведение настоящих серверов (GitHub/GitLab) остаётся на ручные кейсы E2.
* *H3 — снята спайком E0.* Первый доступ JGit к репозиторию измеряет разрешение файловых таймстампов (`FileStoreAttributes`), что могло дать заметную паузу первой операции.
Факт: на устройстве холодная первая операция дороже тёплой на ~60–70 мс — эффект есть, но лечения конфигом не требует — <<spike-e0-h3>>.
* *H4 — проверена спайком E4, вердикт «формулировка опровергнута, вывод в силе».*
Утверждение «Keystore не подписывает ed25519» на актуальном Android неверно: ключ генерируется и подписывает — но только при `setDigests(DIGEST_NONE)` и в DER-обёртке, тогда как SSH требует сырые 64 байта.
Практический вывод не изменился: приватный ключ живёт файлом в хранилище секретов, зашифрованным ключом из Keystore — <<spike-e4-h4>> и xref:../../adr/adr-015-ssh-key-storage.adoc[ADR-015].
* *H5 — подтверждена спайком E0.* Убийство процесса системой посреди операции оставляет stale-lock (`.git/index.lock`), и следующая операция падает с `LockFailedException`.
Проверено фактом через `am force-stop` с занятым lock; протокол лечения — удалить lock-файл и повторить — <<spike-e0-h5>>.

[#spike-e0]
== Спайк E0 (SL-0) — JGit 7.x на устройстве, фактами

Стенд:: Samsung SM-S948B (Android 16, API 36), подключение по adb.
JGit `7.7.1.202607240634-r` (актуальный релиз), AGP 9.3.1, JDK 21.
Прототип — выбрасываемый инструментальный тест `androidApp/src/androidTest/kotlin/io/github/olegnyr/adocmobile/git/JGitSpikeTest.kt`; каждый замер запускался отдельным `am instrument` (свежий процесс), результаты снимались из logcat (тег `GitSpike`).
Дата прогона — 2026-08-17.

[#spike-e0-build]
=== Факты сборки (до первого запуска)

* *Конвейер device-тестов KMP-модуля (`:shared`) JGit 7.x не пропускает.*
JGit 7.x собран под Java 17 и содержит Java records; задача `mergeExtDexAndroidDeviceTest` падает с точной ошибкой: `ERROR: D8: Invalid build configuration. Attempt to create a global synthetic for 'Record desugaring' without a global-synthetics consumer` (transform `DexingNoClasspathTransform`, параметры `enableGlobalSynthetics=false`).
Свойство `android.useFullClasspathForDexingTransform=true` конвейер не меняет (проверено — параметры transform те же).
Это дефект конвейера `com.android.kotlin.multiplatform.library`, а не несовместимость JGit с ART.
* *Конвейер модуля приложения (`:androidApp`) дексует JGit 7.x штатно.*
Проверено дважды: тестовый APK (`installDebugAndroidTest`) собрался и работал, и основной debug-APK с временной зависимостью `debugImplementation(libs.jgit)` собрался, причём `org/eclipse/jgit/api/Git` найден побайтовым поиском в `classes*.dex`.
Значит JGit в `androidMain` шэрд-модуля (план E1) дексуется конечным приложением без препятствий — джарники зависимостей дексует сборка APK, а не библиотека.
* Мелкий факт для будущих тестов: `filesDir` *тестового* пакета не существует (инструментация живёт в процессе приложения) — JGit падает на `mkdirs`; работать нужно от `targetContext`, чей `filesDir` — ровно приватное хранилище из варианта (а) вопроса OQ-1.

[#spike-e0-h1]
=== H1 — shallow clone по HTTPS на ART: подтверждена

Клон `https://github.com/OlegNyr/adoc-mobile.git` с `depth 1` в приватный `filesDir`, анонимно, без модификаций JGit.

[cols="2,1,1", options="header"]
|===
| Метрика | Прогон 1 | Прогон 2

| Время клона (включая checkout)
| 2260 мс
| 2144 мс

| Объектов получено
2+| 404 (Enumerating 404, Compressing 341, Resolving deltas 8)

| Рабочая копия
2+| 282 файла, 8,6 МБ вместе с `.git`

| Пик кучи JVM сверх фона
| ~22,2 МиБ
| ~23,8 МиБ

| Куча после клона сверх фона
2+| ~7,1 МиБ

| Нативная память
2+| +0,9 МиБ
|===

`HEAD` разрешился, `git log` насчитал ровно 1 коммит, файл `.git/shallow` создан — то есть и `setDepth(1)`, и HTTPS-транспорт, и checkout работают на ART как есть.
Откат на линию 6.x не нужен.

[#spike-e0-h2]
=== H2 — push из shallow-клона: подтверждена (клиентская сторона)

Сценарий целиком в приватном каталоге, без сети: bare-remote (`file://`), в нём история из двух коммитов; shallow clone `depth 1` (32 мс; `log` = 1 коммит, `.git/shallow` создан — локальный транспорт JGit shallow поддерживает); правка, commit, push обратно.

Push из shallow-клона прошёл за 15 мс со статусом `refs/heads/main=OK`; вершина remote после push — новый коммит (проверено чтением bare-репозитория).

Ограничение вывода: сервером здесь был сам JGit (`file://`), поэтому серверные политики GitHub/GitLab (`receive.shallowUpdate` и подобные) этим фактом не закрыты — их проверяют ручные кейсы `TC-27`/`TC-28` в E2.
Со стороны клиента препятствий нет; правка плана из риска «H2 не проходит» (unshallow-fetch перед push) не понадобилась.

[#spike-e0-h3]
=== H3 — пауза первой операции: снята

Цикл `init` + `add` + `commit` трижды в свежем процессе, два независимых прогона:

* прогон 1: холодный 77 мс, тёплые 10 и 10 мс;
* прогон 2: холодный 72 мс, тёплые 9 и 8 мс.

Разовая цена первой git-операции процесса — ~60–70 мс (замер `FileStoreAttributes` в JGit ограничен таймаутом ~100 мс, дальше он уходит в фон).
На этом устройстве эффект есть, но заметной паузой не является: конфиг (`core.filesystem`-атрибуты) не нужен, в требования ничего не добавляется.

[#spike-e0-h5]
=== H5 — stale index.lock после убийства процесса: подтверждена

Честная симуляция: тест берёт `index.lock` штатным `Repository.lockDirCache()` и виснет; хост убивает процесс `am force-stop` (та же механика, которой систему выгружает приложение); разбор — из свежего процесса.

Факты:

* после убийства `.git/index.lock` остаётся на диске;
* следующая операция (`add`) падает: `JGitInternalException: Exception caught during execution of add command`, причина — `org.eclipse.jgit.errors.LockFailedException: Cannot lock …/.git/index. Ensure that no other process has an open file handle on the lock file …/.git/index.lock, then you may delete the lock file and retry`;
* лечение — удалить lock-файл и повторить: следующие `add` и `commit` проходят, репозиторий цел (история и рабочая копия не пострадали).

Сам текст исключения JGit прямо предписывает протокол «убедись, что процесс один — удали lock — повтори»: ровно то, что `NFR-5` требует показать пользователю подтверждением.
Тот же результат воспроизведён и без убийства (lock-файл, созданный руками) — падение и лечение идентичны.

=== Последствия для плана

* *E1 возможен в текущем виде*: JGit 7.7.x работает на ART, откат на 6.x и пересмотр фичи не требуются; риск «JGit 7.x не заводится на ART» из `plan.adoc` снят.
* *Одна правка E1 обязательна*: device-тесты Git-цикла не могут жить в `shared/src/androidDeviceTest` — конвейер дексации device-тестов KMP-модуля падает на records из JGit (см. <<spike-e0-build>>).
Варианты: (а) держать Git-device-тесты в `androidApp/src/androidTest` (спайк уже идёт этим путём, работает); (б) дождаться починки AGP; (в) откат на JGit 6.x ради одного лишь тестового конвейера — плохо, версии продукта и тестов разъедутся.
До починки AGP рабочий вариант — (а); список `:targets:` аналитики при активации E1 нужно уточнить.
* Риск «push из shallow не проходит» снят для клиентской стороны; unshallow-fetch перед push в план не добавляется, серверные оговорки уходят в ручные кейсы E2.
* H3 в требования не конвертируется: паузы, требующей прогресс-индикатора или конфига, нет.
* Протокол NFR-5 подтверждён исполнимым: обнаружение `LockFailedException` + удаление `index.lock` с подтверждением пользователя + повтор операции.

== Спайк E4 (SL-15) — ed25519 в Keystore и MINA sshd на ART

Стенд:: Samsung SM-S948B (Android 16, API 36), JGit `7.7.1` + `org.eclipse.jgit.ssh.apache` той же версии.
Прототип — выбрасываемый инструментальный тест `androidApp/src/androidTest/.../SshSpikeTest.kt`; результаты снимались из logcat (тег `SshSpike`).
Дата прогона — 2026-08-18.

[#spike-e4-build]
=== Факт сборки: sshd и `META-INF`

Apache MINA sshd тянет зависимости с одинаковыми путями `META-INF`, и упаковка APK падает:
`2 files found with path 'META-INF/DEPENDENCIES'`.
Дубль не один: следом всплывает `OSGI-INF/l10n/plugin.properties` — его несут и сам JGit, и его SSH-бандл, и вторая ошибка приходит только после починки первой.
Лечится блоком `packaging { resources { excludes += … } }` в `:androidApp` — это метаданные Maven, в рантайме бесполезные.
Грабли уровня проекта, а не слайса: они повторятся при подключении sshd к любому новому модулю, поэтому продублированы в `CLAUDE.md`.

[#spike-e4-h4]
=== H4 — ed25519 в Android Keystore

[cols="2,3", options="header"]
|===
| Проба | Факт

| `KeyPairGenerator("Ed25519", "AndroidKeyStore")`
| OK — ключ генерируется (API 36)

| `KeyPairGenerator(EC)` с `ECGenParameterSpec("ed25519")`
| OK — тоже генерируется

| Провайдеры с Ed25519 в системе
| `AndroidKeyStoreBCWorkaround`, `AndroidKeyStore`

| Приватный ключ: `format` / `encoded`
| `null` / `null` — материал неизвлекаем, как и обещает Keystore

| Подпись `Signature("Ed25519")` без `setDigests`
| FAIL — `InvalidKeyException: Keystore operation failed` ← `KeyStoreException: Incompatible digest`

| То же с `setDigests(DIGEST_SHA512)`
| FAIL — та же `Incompatible digest`

| То же с *`setDigests(DIGEST_NONE)`*
| *OK* — подпись выдаётся, длина 72 байта (DER)

| `Signature("NONEwithEdDSA")`
| FAIL — `NoSuchAlgorithmException: NONEwithEdDSA Signature not available`

| `Signature("EdDSA")`
| FAIL — `InvalidKeyException: No installed provider supports this key`

| Контроль: ed25519 обычным провайдером (не Keystore)
| OK — подпись создаётся и проверяется, публичный ключ 44 байта X.509
|===

Вердикт:: Формулировка гипотезы неверна (подпись работает при `DIGEST_NONE`), но её вывод — «приватный ключ хранить файлом, зашифрованным ключом из Keystore» — остаётся в силе: DER вместо сырых 64 байт, ожидание обычного `KeyPair` со стороны MINA sshd и `minSdk 26`.
Решение записано xref:../../adr/adr-015-ssh-key-storage.adoc[ADR-015].

=== ADR-007 — MINA sshd на ART: подтверждён

`SshdSessionFactory` грузится и инстанцируется на устройстве; доступны `SshdSessionFactoryBuilder` и `ServerKeyDatabase` — последний и есть точка политики host key (`FR-29`), то есть подтверждение неизвестного ключа пользователем реализуемо штатным API, без своего транспорта.
Риск `ADR-007` «работоспособность связки JGit 7.x + sshd на ART» снят.

Важное уточнение из журналов 003::
В `doc/features/003-render-preview/progress.adoc` (строка про чтение соседней картинки) вариант «клонированный репозиторий читается без SAF» упомянут как *возможность*, на которую можно отложить проблему, — решением он нигде не зафиксирован.
Разведка подтверждает физическую основу: JGit работает только с `java.io.File`, поэтому клон обязан лежать там, где у приложения есть прямой файловый доступ.
Но критерий xref:../../user-stories.adoc#US-E5-01[US-E5-01] «клон кладётся обычной папкой: другие приложения видят те же файлы» с приватным хранилищем *несовместим* — это противоречие, и оно вынесено в открытый вопрос аналитики (OQ-1), а не решено здесь.

== Ограничения и риски, найденные разведкой

* JGit требует прямого файлового доступа (`java.io.File`) → клон не может жить в SAF-дереве пользователя; выбор места хранения — развилка OQ-1, задевающая критерий `US-E5-01`.
* `minSdk 26` — жёсткий пол для JGit и MINA sshd на Android; наш проект уже на нём, повышать не нужно.
* JGit 7.x требует Java 17 — сборке это не мешает (JDK 21); работоспособность на ART подтверждена спайком E0 (<<spike-e0-h1>>).
* Конвейер дексации device-тестов KMP-модуля не пропускает джарники с Java records (JGit ≥ 7.0) → Git-device-тесты живут в `androidApp/src/androidTest`, пока AGP не починен (<<spike-e0-build>>).
* SSH-транспорт фактически безальтернативен: JSch-бандл deprecated и не умеет ed25519 → решение фиксируется xref:../../adr/adr-007-ssh-transport.adoc[ADR-007].
* `EncryptedSharedPreferences` deprecated → хранение секретов проектируется на Android Keystore (+ файл/DataStore), выбор конкретной схемы — развилка OQ-2.
* Память: мобильная куча против `WindowCache` и полного чтения индексных файлов → фича заявляется для репозиториев документации, а не монорепо; `depth 1` — основная митигация объёма; порог размера в требованиях не выдумываем, меряем спайком.
* Убийство процесса — штатная жизнь Android → протокол обработки stale-lock и незавершённого клона обязан быть в требованиях (H5).
* Счётчик `↓N` (behind) существует только после fetch — без сетевого обращения он либо нулевой, либо устаревший; периодичность fetch — развилка OQ-5.

== Ответы на вопросы разведки

* *Q1* — да: линия 7.x (Java 17, наш JDK 21) и `minSdk 26` совместимы по требованиям, а работа 7.7.1 на ART подтверждена спайком E0 фактом клона по HTTPS (<<spike-e0-h1>>); оговорка — конвейер device-тестов KMP-модуля (<<spike-e0-build>>).
* *Q2* — HTTPS-токен: `UsernamePasswordCredentialsProvider(token, "")`; SSH: `org.eclipse.jgit.ssh.apache` (MINA), работает на Android по прецеденту orgzly; JSch — тупиковая ветка. Нужен UI подтверждения host key.
* *Q3* — да, с JGit 6.3: `setDepth(1)` на `CloneCommand`/`FetchCommand`. Непроверенное место — push из shallow (H2).
* *Q4* — только хранилище с прямым File-доступом; совместимость с «другие приложения видят файлы» не решается разведкой — противоречие вынесено в OQ-1 аналитики.
* *Q5* — `EncryptedSharedPreferences` deprecated (security-crypto 1.1.0-alpha07); направление платформы — Android Keystore напрямую, данные — файл или DataStore, шифрованные ключом из Keystore. Схема — OQ-2, для SSH-ключа см. H4.
* *Q6* — память ограничивает размер репозитория (WindowCache, индекс в памяти); stale-lock после убийства процесса — H5.
* *Q7* — швы document-слоя, паттерны моделей экранов, чертёжный блок, паттерн device-тестов; новая работа — File-реализация доступа, сам Git-слой и четыре экрана.
