== Видение

Проблема::
Редактор без надёжной работы с файлом бесполезен, и опаснее всего здесь не отсутствие функции, а её ненадёжность.
Потерянные правки — единственный отказ, который пользователь не прощает: подсветку можно потерпеть, вылет пережить, а исчезнувший абзац, который писали в метро, — нет.
Мобильная среда работает против нас: система выгружает приложение без предупреждения, доступ к файлу выдаётся временно и может быть отозван, места на устройстве может не хватить.

Для кого::
*Автор заметок* — правит `.adoc` там, где файл уже лежит, без Git и без импорта в приложение.
*Инженер* — то же самое внутри рабочей папки репозитория.
Обоим важно, чтобы файл остался тем же файлом: не переехал в песочницу приложения, не сменил переводы строк, не потерял кодировку.

Желаемый результат::
Пользователь открывает файл через системный диалог, правит, и текст сохраняется сам.
Приложение, закрытое системой, при следующем запуске возвращает документ в том виде, в каком его оставили.
Отмена работает шагами, соответствующими смыслу правки, а не отдельным символам.
Проверяемо: xref:../../user-stories.adoc#US-E1-01[US-E1-01], xref:../../user-stories.adoc#US-E1-02[US-E1-02], xref:../../user-stories.adoc#US-E1-03[US-E1-03].

Не-цели::
+
--
* *Не файловый менеджер.* Своего браузера файлов у приложения нет — открытие идёт системным диалогом.
Дерево файлов репозитория (`US-E1-04`) относится к Git-итерации, а не сюда.
* *Не несколько документов одновременно.* Вкладок и списка недавних в MVP нет.
* *Не синхронизация и не облако.* Файл живёт там, где его положил пользователь.
* *Не восстановление после сбоя из журнала правок.* Автосохранение по паузе — да; журнал операций с проигрыванием — нет.
* *Не своя история отмены.* Разведка показала, что встроенная в `TextFieldState` подходит по правилам группировки.
--

Ценность и почему сейчас::
Без этой фичи редактор не может открыть ни одного настоящего файла — всё остальное работает на синтетических строках.
Она же снимает самый неприятный класс отказов, а такие вещи дешевле закладывать в основание, чем добавлять поверх готового редактора.

Что изменила разведка::
+
--
*Своё undo/redo писать не нужно.*
Встроенный механизм `TextFieldState.undoState` группирует непрерывный ввод по правилам, которые совпадают с требованием: слияние в пределах 5 секунд, только однотипные правки, перевод строки не сливается.
Программная вставка (панель быстрой вставки) попадает в историю одним нераздельным шагом — то есть `US-E1-03` выполняется встроенным поведением, а не нашим кодом.
Задача `T-040` сжимается вдвое.

*Но API помечен экспериментальным*, и это требует решения владельца, а не умолчания.

*Документация Compose в этом месте расходится с кодом.*
KDoc утверждает, что программные правки очищают историю целиком; код делает обратное.
Мы опираемся на код версии 1.11.2 — значит при обновлении Compose проверку нужно повторять, и это входит в требования.
--

== Требования

[NOTE]
Приоритет по MoSCoW: *M* обязательно для MVP, *S* желательно, *C* можно, *W* не в этот раз.
Требования, зависящие от неотвеченных вопросов, помечены явно.

=== Функциональные: открытие файла

FR-1 (M)::
Открытие ДОЛЖНО идти через системный диалог выбора файла.
Своего файлового менеджера у приложения нет.

FR-2 (M)::
Выданный доступ ДОЛЖЕН удерживаться постоянным разрешением, переживающим перезапуск приложения.

FR-3 (M)::
Отзыв или потеря доступа ДОЛЖНЫ обрабатываться как штатный сценарий, а не как сбой: пользователь видит понятное сообщение и может выбрать файл заново.
Основание: разведка показала, что постоянное разрешение не гарантировано навсегда.

FR-4 (M)::
Файл ДОЛЖЕН читаться как UTF-8.
Тип переводов строк (LF, CRLF, CR) определяется при чтении и *хранится в модели документа*, а не выводится из текста при записи: пользователь мог удалить все переводы строк.

FR-5 (M)::
При записи ДОЛЖЕН восстанавливаться исходный тип переводов строк.
Файл с CRLF не переписывается в LF.

FR-5a (M)::
Файл со *смешанными* переводами строк ДОЛЖЕН приводиться к одному типу — тому, что встретился первым.
+
[IMPORTANT]
.Решение принято по итогам ревью SL-1, и у него есть цена
====
Ревью справедливо указало, что цикл «открыть — ничего не тронуть — сохранить» для смешанного файла не тождественный: строки, которых пользователь не касался, меняют окончание, и в Git это диф на весь файл вместо одной правленой строки.
С автосохранением из `SL-4` это произойдёт даже если документ просто открыли и свернули приложение.

Нормализация выбрана сознательно — так поступает большинство редакторов, и альтернатива (хранить исходный текст и переписывать только тронутые строки) стоит отдельной структуры данных ради файла, который и так уже непоследователен.

Но решение обязано быть *записанным*, а не жить в комментарии к коду: до ревью его не было ни здесь, ни в ADR, ни в разведке.
Закреплено кейсом `TC-9c`.
====

FR-6 (S)::
Открытие файла около 1000 строк НЕ ДОЛЖНО блокировать интерфейс.
Порог размера — xref:../../adr/adr-004-document-size-limit.adoc[ADR-004].

=== Функциональные: модель документа

FR-7 (M)::
Модель документа ДОЛЖНА хранить: текст, ссылку на источник, тип переводов строк, признак несохранённых изменений, отметку времени последней успешной записи.

FR-8 (M)::
Признак несохранённых изменений ДОЛЖЕН отражать реальное расхождение с записанным на диск, а не факт касания текста.
Правка и отмена этой правки возвращают документ в сохранённое состояние.
+
[NOTE]
Требование выглядит мелким, но именно оно отличает честный индикатор от пугающего: иначе метка «не сохранён» горит после любого нажатия клавиши, даже когда текст вернулся к исходному.

FR-9 (M)::
Модель документа ДОЛЖНА быть в `commonMain` и не зависеть от платформенных типов файлового доступа.
Платформенным остаётся только шов чтения и записи.

=== Функциональные: отмена и повтор

FR-10 (M)::
Отмена и повтор ДОЛЖНЫ использовать встроенную историю `TextFieldState`.
Своя история не пишется.

FR-11 (M)::
Шаг отмены ДОЛЖЕН группировать непрерывный ввод.
Обеспечивается встроенными правилами; наша обязанность — *проверить их тестом*, а не реализовать.

FR-12 (M)::
Вставка конструкции с панели быстрой вставки ДОЛЖНА отменяться одним шагом.
Обеспечивается тем, что программная правка не сливается с соседними.

FR-13 (S)::
Отмена и повтор ДОЛЖНЫ быть доступны из меню документа и с аппаратной клавиатуры.

FR-14 (C)::
При загрузке нового документа история отмены ДОЛЖНА очищаться: отменить правку в файл, который уже закрыт, нельзя.

FR-15 (M)::
Проверка совпадения встроенного поведения с `FR-11` и `FR-12` ДОЛЖНА выполняться тестом, который сломается при смене поведения Compose.
Основание: документация Compose расходится с кодом, область не устоялась.

=== Функциональные: сохранение

FR-16 (M)::
Правки ДОЛЖНЫ сохраняться по паузе ввода и при уходе приложения в фон.

FR-17 (M)::
Отказ записи (нет прав, нет места, файл исчез) ДОЛЖЕН показываться пользователю, а несохранённый текст — оставаться в памяти.
Молчаливой потери правок не происходит.

FR-18 (M)::
Состояние документа ДОЛЖНО быть видно в заголовке экрана: `ИЗМЕНЁН · НЕ СОХРАНЁН` до записи, чистое имя файла после.

FR-19 (S)::
Повторный отказ записи НЕ ДОЛЖЕН приводить к бесконечным попыткам: после неудачи автосохранение приостанавливается до следующей явной правки или до ручного повтора.

FR-20 (M)::
Запись идёт *напрямую* в файл пользователя; атомарность не гарантируется.
Решение владельца 2026-08-17.
+
[WARNING]
.У решения есть цена, и она записана здесь намеренно
====
Обрыв записи — кончилось место, система сняла процесс — оставит файл наполовину записанным.
Приём «временный файл и замена», который это лечит, для `content://` URI разведкой не подтверждён, и проверять его отдельным прогоном признано неоправданным.

Смягчает риск `FR-17`: несохранённый текст остаётся в памяти, поэтому после обрыва пользователь может повторить запись, а не остаться ни с чем.
Полностью риск не снят, и если повреждение файлов проявится на практике, решение пересматривается — приём проверяется на устройстве, и требование переформулируется.
====

=== Нефункциональные

Отзывчивость::
Чтение и запись — вне главного потока.
Сохранение не блокирует ввод: пользователь продолжает печатать во время записи.

Доля общего кода::
Модель документа, признак изменений, политика автосохранения — в `commonMain`.
Платформенным остаётся шов файлового доступа.

Офлайн::
Применимо целиком: фича работает без сети по определению.

Платформенный паритет::
Шов проектируется под обе платформы, реализуется пока только Android — xref:../../adr/adr-002-android-first.adoc[ADR-002].

Жизненный цикл::
Уход в фон, выгрузка системой и поворот экрана не теряют текст.
Это главное нефункциональное требование фичи, а не одно из.

Файлы пользователя::
Файл не копируется в песочницу приложения и не переименовывается.
Правится тот файл, который выбрал пользователь.

Ввод и IME::
Автосохранение не должно прерывать композицию IME.

Секреты::
Неприменимо: приложение не хранит учётных данных на этом этапе.

Доступность::
Состояние документа передаётся текстом, а не только цветом метки.

Тестируемость::
Политика автосохранения и признак изменений проверяются в `commonTest` без устройства.
Файловый шов проверяется на устройстве отдельно.

=== Ограничения и допущения

* Размер документа — около 1000 строк (xref:../../adr/adr-004-document-size-limit.adoc[ADR-004]).
* Один открытый документ за раз.
* Постоянное разрешение доступа не гарантировано навсегда — это допущение платформы, а не наше решение.
* Опора на встроенное undo привязывает нас к поведению Compose 1.11.2; при обновлении требуется перепроверка (`FR-15`).

== Сценарии использования

=== UC-1 — открыть файл

Триггер:: `user`.
Основной сценарий:: пользователь выбирает файл системным диалогом → приложение удерживает постоянное разрешение → читает UTF-8, определяет тип переводов строк → текст доступен для правки.
Расширения::
+
* Файл не UTF-8 → сообщение, файл не открывается (поведение — см. открытые вопросы).
* Доступ отозван → `FR-3`.
Покрывает:: FR-1…FR-6.

=== UC-2 — правка и автосохранение

Триггер:: `user` — ввод текста.
Основной сценарий:: правка → признак несохранённых изменений → пауза ввода → запись → признак гаснет.
Расширения::
+
* Уход в фон до истечения паузы → запись немедленно.
* Отказ записи → `FR-17`, `FR-19`.
* Правка отменена до записи и текст совпал с сохранённым → признак гаснет без записи (`FR-8`).
Покрывает:: FR-7, FR-8, FR-16…FR-19.

=== UC-3 — отмена правок

Триггер:: `user`.
Основной сценарий:: пользователь вызывает отмену → возвращается состояние до последней группы правок.
Расширения::
+
* Отменяется вставка с панели → уходит целиком одним шагом.
* История исчерпана → отмена недоступна, а не бросает ошибку.
Покрывает:: FR-10…FR-14.

=== UC-4 — приложение выгружено системой

Триггер:: `system-event`.
Смысл сценария:: это не редкий случай, а нормальная жизнь мобильного приложения.
Основной сценарий:: система выгружает процесс → пользователь возвращается → документ открыт, текст на месте.
Покрывает:: NFR жизненного цикла, FR-2, FR-16.

== Тест-кейсы

=== Модель и признак изменений

TC-1 (happy, automatable):: Документ, прочитанный из источника, имеет признак «сохранён».
TC-2 (happy, automatable):: Правка поднимает признак несохранённых изменений.
TC-3 (edge, automatable):: Правка и возврат текста к сохранённому состоянию признак *снимают* (`FR-8`).
TC-4 (happy, automatable):: Успешная запись снимает признак и обновляет отметку времени.
TC-5 (negative, automatable):: Неудачная запись признак не снимает.

=== Переводы строк и кодировка

TC-6 (happy, automatable):: Файл с CRLF читается, правится и записывается с CRLF.
TC-7 (happy, automatable):: Файл с LF записывается с LF.
TC-8 (edge, automatable):: Документ, из которого удалены все переводы строк, при записи сохраняет исходный тип — он взят из модели, а не выведен из текста (`FR-4`).
TC-9 (edge, automatable):: Кириллица, эмодзи и составные символы переживают цикл чтение-запись без искажения.
TC-9a (edge, automatable):: Файл только с `CR` (классический macOS) читается и записывается с `CR`, а не переводится в `LF`.
TC-9b (edge, automatable):: Файл без единого перевода строки и пустой файл дают `LF` — гадать не о чем, а `LF` не мешает Git.
TC-9c (edge, automatable):: Файл со *смешанными* переводами строк получает тип первого встреченного; при записи весь файл приводится к нему — см. `FR-5a`.
TC-9d (edge, automatable):: Повторное применение типа переводов строк не удваивает возврат каретки: `\r\n` не превращается в `\r\r\n`.

[NOTE]
Кейсы `TC-9a`…`TC-9d` добавлены по итогам ревью `SL-1`.
Соответствующие тесты были написаны сразу, но носили метки `TC-7`, `TC-8` и `TC-9`, которых на деле не проверяли.
Метка, навешенная не на тот кейс, хуже отсутствующей: сверка спеки с кодом отчиталась бы о покрытии, а три принятых решения — поведение для `CR`-файла, для пустого файла и правило «первый встреченный» — остались бы в коде, не имея ни строчки в спеке.

=== Отмена и повтор

TC-10 (happy, automatable):: Непрерывный ввод нескольких символов отменяется одним шагом (`FR-11`).
TC-11 (edge, automatable):: Ввод, разделённый переводом строки, отменяется двумя шагами — перевод строки является границей группы.
TC-12 (happy, automatable):: Программная вставка блока отменяется одним шагом и не сливается с ручным вводом до и после (`FR-12`).
+
Этот тест — страховка от смены поведения Compose, а не проверка нашего кода (`FR-15`).
TC-13 (edge, automatable):: Отмена при пустой истории ничего не делает и не бросает исключение.
TC-14 (edge, automatable):: Загрузка нового документа очищает историю (`FR-14`).

=== Автосохранение

TC-15 (happy, automatable):: Пауза ввода запускает запись ровно один раз, а не на каждый символ.
TC-16 (happy, automatable):: Уход в фон записывает немедленно, не дожидаясь паузы.
TC-17 (negative, automatable):: Отказ записи показывается пользователю, текст остаётся в памяти (`FR-17`).
TC-18 (negative, automatable):: После отказа автосохранение не повторяет попытку бесконечно (`FR-19`).
TC-19 (edge, automatable):: Запись не блокирует ввод: во время записи текст можно менять, и изменение не теряется.

=== Файловый доступ

TC-20 (happy, manual):: Файл, открытый системным диалогом, доступен после перезапуска приложения без повторного выбора.
TC-21 (negative, manual):: После отзыва доступа приложение показывает понятное сообщение и предлагает выбрать файл заново (`FR-3`).
TC-22 (happy, manual):: Приложение, выгруженное системой, при возврате показывает документ с последним сохранённым текстом (`UC-4`).
TC-23 (edge, manual):: Файл около 1000 строк открывается без замирания интерфейса.

== Технический подход

Слои::
+
--
. *Модель документа* (`commonMain`) — текст, источник, тип переводов строк, признак изменений, отметка записи.
. *Политика автосохранения* (`commonMain`) — дебаунс паузы, реакция на уход в фон, поведение после отказа.
Чистая логика, проверяемая без устройства.
. *Шов файлового доступа* (`expect`/`actual`) — минимальный: прочитать, записать, удержать разрешение.
Чем он тоньше, тем больше проверяется в `commonTest`.
--

Точки подражания::
Стиль проверок — задачи сборки в `shared/build.gradle.kts`.
Стиль тестов — `AdocTypographyTest`, `AdocBlueprintGeometryTest`: имя с идентификатором тест-кейса, комментарий объясняет зачем.

Рамки и запреты::
+
--
* *Не писать своё undo* — `FR-10`.
* *Не копировать файл в песочницу* приложения.
* *Не тянуть платформенные типы в модель документа* — `FR-9`.
* *Не расширять шов* сверх чтения, записи и удержания разрешения: всё, что можно решить в общем коде, решается там.
--

== Открытые вопросы

=== Решённое

*Решено 2026-08-17: запись идёт напрямую*, атомарность не гарантируется — уехало в `FR-20` вместе с ценой решения.

*Решено 2026-08-17: встроенная история отмены используется* несмотря на пометку экспериментального API.
Своя история стоит примерно вдвое дороже и повторяет существующую логику; риск снимается тестом-сторожем `TC-12`, а решение обратимо — своя история пишется поверх той же модели.
Уехало в `FR-10` и `FR-15`.

=== Не блокирующие, но нужны до соответствующих слайсов

*Внешнее изменение файла.*
Файл правят другим приложением, пока документ открыт у нас.
Варианты: не замечать (правки перетрут чужие); заметить при записи и спросить; заметить и перечитать.

*Файл не в UTF-8.*
Варианты: отказать с внятным сообщением; попытаться определить кодировку; открыть только для чтения.
