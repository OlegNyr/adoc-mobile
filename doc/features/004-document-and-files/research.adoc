== Undo/redo уже есть в `TextFieldState`

Проверено по исходникам `androidx.compose.foundation` 1.11.2 — той версии, что приходит с Compose Multiplatform 1.11.1.

`TextFieldState.undoState` — публичное свойство типа `UndoState` с методами `undo()`, `redo()`, `clearHistory()` и признаками `canUndo`, `canRedo`.

[IMPORTANT]
Свойство помечено `@ExperimentalFoundationApi`.
В KDoc прямо сказано, почему: undo-часть API остаётся экспериментальной отдельно от самого `TextFieldState`, который уже стабилен.
Это риск, требующий явного решения владельца, — см. открытые вопросы аналитики.

=== Группировка непрерывного ввода реализована и совпадает с требованием

`US-E1-03` требует, чтобы шаг отмены группировал непрерывный ввод, а не отдельный символ.
Встроенный механизм делает ровно это, и правила слияния заданы в `TextUndoOperation.merge`:

* правки сливаются, только если между ними прошло меньше *5000 мс* (`SNAPSHOTS_INTERVAL_MILLIS`);
* сливаются только однотипные правки: вставка со вставкой, удаление с удалением; замена не сливается никогда;
* две вставки сливаются, только если следующая продолжает предыдущую — то есть каретка движется вперёд;
* удаления сливаются, только если совпадает направление (backspace против delete) и они граничат;
* *вставка перевода строки не сливается ни с чем* — абзац становится естественной границей шага отмены.

Ёмкость истории — *100 операций* (`TEXT_UNDO_CAPACITY`), после чего старые вытесняются.

=== Программная вставка — ровно один шаг отмены

Это ключевой факт для `US-E1-03`, где сказано: «вставка конструкции с панели — один шаг отмены».

Здесь документация *вводит в заблуждение*, и на это стоит обратить внимание.
KDoc перечисления `TextFieldEditUndoBehavior` утверждает: «Programmatic updates should clear the history completely».
Если поверить этому, вывод был бы прямо противоположный: панель вставки стирала бы всю историю правок, и своё undo пришлось бы писать обязательно.

Фактический код `commitEdit` делает другое — передаёт `NeverMerge` с комментарием «programmatic edits contribute to undo history without merging».
То есть программная правка через `TextFieldState.edit {}` попадает в историю *одним нераздельным шагом* и не слипается с соседними.

Это в точности то поведение, которого требует история.
Проверено чтением кода версии 1.11.2; при обновлении Compose проверку нужно повторить — расхождение KDoc и кода означает, что область не устоялась.

=== Что из этого следует

Своё undo/redo писать не нужно.
Задача `T-040` сжимается с «реализовать историю правок с группировкой» до «подключить встроенную и проверить, что её правила совпадают с требованиями».

Остаётся выяснить опытом:

* переживает ли история пересоздание активности (у операций есть `Saver`, но сохраняется ли она вместе с состоянием поля — по исходникам не очевидно);
* что происходит с историей при загрузке нового документа в то же состояние поля.

== Файловый доступ

[WARNING]
Раздел не проверялся прогоном: устройство было занято замерами.
Всё ниже — *гипотезы* уровня «так устроен API по документации», и до реализации `T-041` их нужно подтвердить на устройстве.

Android::
Открытие идёт через SAF (`ACTION_OPEN_DOCUMENT`), доступ удерживается `takePersistableUriPermission`.
Право живёт до переустановки приложения или до отзыва пользователем, но *не гарантировано вечно*: система может его потерять при очистке данных, а сам файл — исчезнуть или переехать.
Значит «открыть последний документ при старте» обязано иметь путь отказа, а не считаться безусловно работающим.

iOS::
`UIDocumentPickerViewController` и security-scoped bookmark.
Отложено решением xref:../../adr/adr-002-android-first.adoc[ADR-002], в требованиях учитывается только как форма шва.

Переводы строк::
`US-E1-01` требует сохранять исходный тип переводов строк при записи.
Это означает, что тип определяется при чтении и хранится в модели документа — вывести его из текста при записи нельзя, если пользователь удалил все переводы строк.

Атомарность записи::
Запись поверх исходного файла при обрыве (нехватка места, снятие процесса) оставляет файл повреждённым.
Стандартный приём — запись во временный файл и замена; применим ли он к `content://` URI из SAF, разведкой не подтверждено.
Это *гипотеза*, и она вынесена в открытые вопросы, потому что меняет требование к автосохранению.

== Что осталось непроверенным

. Переживает ли история отмены пересоздание активности.
. Работает ли запись через временный файл с заменой для SAF-URI.
. Поведение при внешнем изменении файла другим приложением, пока документ открыт.
. Сколько времени занимает чтение файла на 1000 строк через `ContentResolver` — от этого зависит, нужен ли индикатор загрузки.
