== Проблема

AsciiDoc — стандарт де-факто для технической документации (docs-as-code, Antora, Spring REST Docs, Confluence-пайплайны), однако мобильная экосистема для него практически пуста.
На Android существуют только устаревшие вьюеры без редактирования (Asciidoc Viewer, последнее обновление — годы назад) и заброшенный форк Markor с поддержкой AsciiDoc, устанавливаемый вручную через APK.
На iOS ситуация не лучше.
Полноценного редактора с live-превью — аналога того, что даёт связка IDE-плагинов на десктопе — на мобильных платформах нет.

Типовой сценарий, который сегодня не закрыт: инженер или технический писатель хочет в дороге поправить документацию, посмотреть результат рендера и закоммитить изменения — без ноутбука.

== Что делаем

Мобильный редактор AsciiDoc с живым превью для Android и iOS, построенный на Kotlin Multiplatform и Compose Multiplatform.

Ключевые свойства продукта:

Нативный редактор с подсветкой синтаксиса::
Не WebView-обёртка над CodeMirror, а нативное текстовое поле Compose с собственным построчным сканером AsciiDoc-синтаксиса.
Это даёт корректную работу клавиатуры, IME, автокоррекции и выделения — то, на чём ломаются WebView-редакторы.

Честный рендер, а не урезанный парсер::
Превью формируется настоящим Asciidoctor (через Asciidoctor.js), то есть результат идентичен тому, что выдаёт десктопный пайплайн: таблицы, admonitions, include-директивы в пределах возможностей мобильного окружения, атрибуты документа.

Полностью офлайн::
Рендер текста выполняется на устройстве, сеть не требуется.
Единственное сетевое исключение — рендер диаграмм (PlantUML/Mermaid через Kroki), результаты которого кэшируются для офлайн-просмотра.

Встроенная Git-синхронизация::
Clone/pull/commit/push прямо из приложения — полный цикл docs-as-code без ноутбука.
Работа с файлами, а не с проприетарной базой: репозиторий на устройстве остаётся обычной папкой, совместимой с любыми другими инструментами.

Единая кодовая база::
Одно приложение на обе платформы; платформенный код сведён к двум тонким адаптерам.

== Целевая аудитория

* Инженеры и техписатели, работающие в docs-as-code процессах (Git + AsciiDoc + CI-публикация в Confluence/Antora/PDF).
* Пользователи, ведущие заметки и личную базу знаний в `.adoc`.
* Вторичная аудитория — читатели: просмотр `.adoc`-файлов из репозиториев и файловых менеджеров (интент на открытие файла).

Пользовательские сценарии в разрезе ролей — в xref:user-stories.adoc[пользовательских историях].

== Продуктовый скоуп

=== MVP

* Открытие/сохранение `.adoc`-файлов через системный файловый диалог (SAF на Android, document picker на iOS).
* Редактор с подсветкой: заголовки, списки, delimited blocks (listing, example, sidebar, comment), инлайн-форматирование, ссылки и макросы, атрибуты.
* Live-превью с раздельным дебаунсом: подсветка ~50–100 мс, рендер ~300 мс.
* Переключение/разделение «редактор ↔ превью» (на планшетах — side-by-side).
* Автосохранение, undo/redo.
* Тёмная тема.

=== Следующие итерации

* Панель быстрой вставки конструкций (toolbar: bold, mono, таблица, admonition, блок кода) — критично для мобильного ввода.
* *Встроенная Git-синхронизация* (подтверждённая фича продукта): clone по HTTPS/SSH, pull, commit, push, история изменений файла; авторизация по токену/ключу.
Реализация — `expect`/`actual` поверх платформенных библиотек (JGit на Android; на iOS — libgit2 через Kotlin/Native-интероп).
Конфликты в первой версии решаются просто: предупреждение и выбор «моя версия / их версия», полноценный merge-редактор — позже.
До появления Git-слоя переходное решение — корректная работа с папками, синхронизируемыми сторонними клиентами (Syncthing, рабочие папки Git-клиентов).
* *Рендер диаграмм (PlantUML, Mermaid и др.) через Kroki.*
Классический asciidoctor-diagram требует локальной Java и Graphviz — на мобильном это нереализуемо, поэтому используем расширение asciidoctor-kroki: оно работает внутри Asciidoctor.js и превращает блоки `[plantuml]`/`[mermaid]` в ссылки на изображения, которые рендерит Kroki-сервер (по умолчанию публичный kroki.io; URL настраивается).
Отрендеренные изображения кэшируются на устройстве, чтобы превью не ломалось офлайн; без сети и кэша блок диаграммы показывается как код с пометкой.
* *Экспорт в PDF.*
Asciidoctor-pdf — Ruby-инструмент, в JS-версии недоступен, поэтому путь другой: готовый HTML из нашего же рендера печатается в PDF платформенными средствами — `PrintManager`/`createPrintDocumentAdapter` у WebView на Android и `WKWebView.createPDF`/`UIPrintPageRenderer` на iOS.
Плюс печатная CSS-тема (разрывы страниц по секциям, колонтитулы).
Результат — в share sheet.
* *Диагностика документа.*
AsciiDoc почти не имеет синтаксических ошибок в компиляторном смысле: неверная разметка не ломает рендер, а остаётся текстом.
Ловить нужно другое — неразрешённый `include`, ссылку на несуществующий якорь или атрибут, незакрытый delimited-блок, перескок уровня заголовка, дублирующийся id.
Отдельный валидатор для этого не пишется: сообщения снимаются с логгера Asciidoctor (`MemoryLogger` через `LoggerManager`) в том же проходе, что и превью, с номерами строк по `sourcemap`; быстрые структурные проверки даёт сканер подсветки, который и так ведёт состояние блока построчно.
Диагностика идёт по паузе ввода и не проверяет блок под кареткой — иначе незакрытый блок помечается ошибкой всё время, пока его печатают.
Показываем `ERROR` и `WARN`; стилистических придирок не показываем — это редактор для правок в дороге, а не линтер в CI.
* *Проверка орфографии.*
Автокоррекция и подсказки клавиатуры работают сами — это поведение IME, отдельной фичей не считается.
Речь о подчёркивании опечаток в самом поле: Compose рисует текст сам и не наследует системную проверку `TextView`, поэтому нужны `SpellCheckerSession` (`TextServicesManager`) на Android и `UITextChecker` на iOS, а отрисовка подчёркивания — наша.
Это третий `expect`/`actual`-шов вдобавок к рендеру и превью, и он бьёт по цели «доля платформенного кода ≤ 20 %» — поэтому фича стоит ниже диагностики по приоритету.
Ценность даёт не словарь, а фильтрация: проверять нельзя код-блоки, инлайн-моноширинный текст, имена атрибутов, URL и цели макросов — границы всего этого сканер подсветки уже знает.
Отдельный риск — двуязычный текст: английские термины в русской фразе споткнут любой словарь, и настройкой это не лечится.
* Экспорт в standalone HTML, share sheet.
* Номера строк, поиск по документу, поддержка include с локальными файлами.

=== Сознательно вне скоупа

* Автодополнение и сворачивание блоков (десктопные паттерны, на мобильном не окупаются).
* Собственная реализация парсера AsciiDoc — используем референсный движок.
* WYSIWYG-режим.

== Архитектура

=== Общий принцип

Максимум логики в `commonMain`; платформенная специфика изолирована за двумя узкими интерфейсами: JS-движок для рендера и обёртка превью.
Оценочная доля общего кода — 80–85 %.

=== Слои

UI (commonMain, Compose Multiplatform)::
Экран редактора на `BasicTextField` с `TextFieldState` (новое API — избегаем лишних рекомпозиций на больших текстах).
Подсветка через `OutputTransformation`: трансформация применяется к отображению, не мутируя текст.

Подсветка (commonMain)::
Построчный сканер: AsciiDoc почти полностью строчно-ориентирован, поэтому достаточно однопроходного конечного автомата (обычный текст / внутри listing / внутри example / внутри comment) плюс инлайн-регексы для строк в «обычном» состоянии.
Выход — платформенно-нейтральный список диапазонов `(range, style)`, кэшируется.
Инкрементальность: при правке пересканируется участок от ближайшей границы блока выше изменения до первой строки со совпавшим состоянием.

Рендер (expect/actual)::
Интерфейс: `suspend fun render(source: String): String` — AsciiDoc на входе, HTML на выходе.
+
--
* *Android:* headless JS-движок (QuickJS или J2V8) с загруженным бандлом asciidoctor.js — синхронные вызовы в фоновом потоке, без привязки к WebView и main thread.
* *iOS:* системный JavaScriptCore через Kotlin/Native-интероп (`platform.JavaScriptCore.JSContext`) — без WebView, быстрее и легче WKWebView.
* Движок и загруженный бандл живут синглтоном: инициализация Opal-рантайма Asciidoctor.js дорогая, выполняется один раз.
* Передача документа в JS — только через строгую сериализацию (JSON-эскейп), защита от инъекций на спецсимволах.
--

Превью (expect/actual)::
`AndroidView { WebView }` / `UIKitView { WKWebView }` либо готовая обёртка compose-webview-multiplatform.
Превью получает готовую HTML-строку от рендера.

Файлы и состояние (commonMain)::
okio/kotlinx-io, модель документа, undo/redo, автосохранение, пайплайн дебаунсов на корутинах.

=== Схема потока данных

[source,text]
----
ввод пользователя
   └─> TextFieldState ──┬─> сканер подсветки (50–100 мс) ─> OutputTransformation
                        └─> рендер Asciidoctor.js (300 мс) ─> HTML ─> WebView-превью
----

== Ключевые технические решения и их обоснование

[cols="1,1,2", options="header"]
|===
| Решение | Альтернатива | Почему так

| Нативный редактор Compose
| CodeMirror в WebView
| Мост «клавиатура ↔ contenteditable» — источник худших мобильных багов; состояние в JS ломает единый источник правды в Kotlin; редактор перестаёт быть общим кодом

| Asciidoctor.js как движок
| Собственный парсер / Go-порт
| Полная совместимость с референсной реализацией; нативные порты неполны, спецификация языка ещё в работе (Eclipse Foundation)

| Headless JS-движок на Android
| `evaluateJavascript` в WebView
| Синхронность, фоновый поток, рендер не привязан к жизненному циклу вью

| Самописный сканер подсветки
| Порт грамматики CodeMirror
| Сканер — общий Kotlin-код на обе платформы; строчная природа AsciiDoc делает его компактным (референс покрытия — регексы Markor-форка)

| `TextFieldState` + `OutputTransformation`
| `value`/`onValueChange` + `VisualTransformation`
| Производительность на больших документах, меньше пересозданий строки
|===

== Риски

Производительность Compose-текстфилда на очень больших файлах (десятки тысяч строк)::
Митигация: ранний стресс-тест; запасной план — `expect`/`actual` на само поле ввода (`Spannable` / `NSAttributedString`) с сохранением общего ядра подсветки, поскольку сканер выдаёт платформенно-нейтральные диапазоны.

Скорость рендера Asciidoctor.js (Opal-рантайм) на слабых устройствах и больших документах::
Митигация: дебаунс, рендер только по паузе ввода, тёплый синглтон движка; при необходимости — рендер видимой части.

`include` и внешние ресурсы в песочнице мобильных ОС::
Митигация: в MVP `include` ограничен файлами в пределах выданного доступа (tree URI / security-scoped bookmark), остальное — деградация с предупреждением в превью.

Compose Multiplatform на iOS::
Стабилен, но текстовый ввод остаётся самой чувствительной областью; закладываем время на полировку UX клавиатуры.

Git-слой несимметричен по платформам::
На Android есть зрелый JGit, на iOS придётся интегрировать libgit2 через C-интероп — это самая трудоёмкая платформенная часть проекта.
Митигация: Git выделен в отдельную итерацию после MVP; интерфейс синхронизации абстрагирован, чтобы Android-версия могла выйти с Git раньше iOS.

Диаграммы зависят от внешнего сервиса::
По умолчанию используется публичный kroki.io — для пет-проекта и типовых пользователей это нормально.
Настройка собственного Kroki-URL остаётся в опциях для тех, кто работает с чувствительными документами; при недоступности сервера блок диаграммы деградирует до кода с пометкой.

== Критерии успеха MVP

. Открыть `.adoc` на 2–3 тыс. строк, редактирование без заметных лагов (подсветка < 100 мс, ввод без пропуска кадров).
. Превью совпадает с выводом десктопного Asciidoctor на тестовом корпусе документов (таблицы, admonitions, блоки кода, атрибуты).
. Полный цикл «открыл — поправил — сохранил — поделился/закоммитил» проходит без ноутбука.
. Одна кодовая база собирается на обе платформы; доля платформенного кода ≤ 20 %.

== Почему сейчас

Ниша фактически пустая: существующие решения мертвы или не выходят за рамки просмотра.
Одновременно созрели все технологические компоненты — Compose Multiplatform стабилен на iOS, `TextFieldState`/`OutputTransformation` решили проблему производительности текстовых полей, Asciidoctor.js даёт полный движок без Ruby-рантайма на устройстве.
Стоимость входа в качественный продукт снизилась до уровня, посильного маленькой команде или одному разработчику.
