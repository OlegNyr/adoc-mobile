== Состояние API

`OutputTransformation` *стабилен*: в исходниках androidx у него единственная аннотация `@Stable`, экспериментальных пометок нет.
Подсветка через `OutputTransformation` + `TextFieldBuffer.addStyle` — официально поддержанный путь, прямо описанный в документации к интерфейсу.

Проект сидит на Compose Multiplatform 1.11.1, что соответствует Jetpack Compose 1.11.2, — на поколение позади текущего стабильного 1.12.0.

За последний год `BasicTextField` заметно правили: две отдельные оптимизации расчёта размеров (флаги `isBasicTextFieldMinSizeOptimizationEnabled` в 1.11, `isBasicTextFieldHeighInLinesOptimizationEnabled` в 1.12) и починка `IndexOutOfBoundsException` при удалении текста с активным `OutputTransformation`.
Это признак, что область горячая.

== Ключевое ограничение

Документация `OutputTransformation` прямо сообщает: трансформация вызывается *каждый раз, когда нужно отобразить новый текст*, буфер при вызове содержит *всё* текущее содержимое, а изменения отбрасываются после показа — то есть результат между вызовами не кэшируется.

Следствие для архитектуры, и оно жёсткое: класть проход сканера внутрь `transformOutput` нельзя.
Сканер должен держать диапазоны в отдельном состоянии, а `transformOutput` — только расставлять стили, и желательно лишь для диапазонов вокруг видимой области.

Ограничение видимой областью — индустриальный стандарт для редакторов, а не наша выдумка; так работают и профильные библиотеки, и десктопные редакторы.

== Публичных цифр предела не существует

Это отдельный результат разведки, и он негативный:

* в документации Android нет ни одного числа — ни в символах, ни в строках, ни в миллисекундах — как границы применимости `BasicTextField`;
* тикеты в `issuetracker.google.com` закрыты за авторизацией и не поддаются проверке;
* единственное найденное свидетельство о деградации относится к Compose Desktop 2023 года и к нашему случаю почти не применимо.

Значит `T-010` — не перестраховка: это единственный способ узнать собственный предел.
Ссылаться в критериях приёмки будет не на что, кроме своих замеров.

== Уточнение нашего критерия

Видение задаёт «подсветка < 100 мс».
Разведка показывает, что это осмысленно только для *холодного полного прохода* при открытии документа.

Для набора текста критерий бесполезен: чтобы не терять кадры, инкрементальный проход должен укладываться примерно в 16 мс, то есть быть на порядок дешевле.
Иначе `T-024` формально пройдёт, уложившись в 100 мс, и ввод всё равно будет рваным.

Предлагается разделить порог на два и внести это в видение отдельным решением.

== Методика замера

Три уровня, три инструмента. Один прогон оба критерия не закрывает.

=== Уровень A — логика сканера

Инструмент:: `kotlinx-benchmark` 0.4.17 из общего кода (даёт число и для Android, и для iOS), критичные случаи продублировать микробенчмарком `androidx.benchmark:benchmark-junit4` 1.4.1 на устройстве ради реального ARM.
Корпус:: документы на 500 / 1000 / 2000 / 3000 / 5000 строк с блоками listing, example, comment и плотной инлайн-разметкой.
Сценарии:: полный холодный проход; инкрементальный после правки одного символа в середине; правка внутри незакрытого блока — худший случай, когда состояние строк долго не сходится.
Пороги:: инкрементальный проход P95 < 16 мс; полный холодный проход на 3000 строк < 100 мс.

=== Уровень B — плавность ввода

Инструмент:: `androidx.benchmark:benchmark-macro-junit4`, стабильная 1.4.1 либо 1.5.0-rc01 ради нового API UiAutomator.
Обвязка:: `Modifier.testTag` на поле, `testTagsAsResourceId = true`, сборка profileable non-debuggable.
Сценарий:: курсор в *середину* документа (конец дешевле и даёт заниженный результат), 60–100 нажатий с интервалом ~50 мс; отдельно — ввод внутри listing-блока; отдельно — прокрутка при активной подсветке.
Метрики:: `FrameTimingMetric` даёт `frameDurationCpuMs` и `frameOverrunMs`; последняя доступна только на API 31+. Плюс `TraceSectionMetric` по своим секциям вокруг прохода сканера.
Пороги (предложение, уточняется первым же прогоном):: `frameOverrunMs` P95 ≤ 0 и P99 < 4 мс; `frameDurationCpuMs` P95 < 8 мс; медиана времени пересканирования < 16 мс за итерацию.

Документация прямо подсказывает трактовку: если `frameOverrunMs` уходит в положительные значения на высоких перцентилях, значит рекомпозиции блокируют главный поток.

=== Уровень C — диагностика при пробое порога

Composition tracing (`runtime-tracing` + `tracing-perfetto`) с аргументом `androidx.benchmark.fullTracing.enable=true`, режимы профилирования `MethodTracing` и `StackSampling`.
Для полевых прогонов — JankStats с разметкой состояния «печать, размер документа N».

== Эмулятор не подходит

Позиция документации однозначна: запускать бенчмарки на эмуляторе не рекомендуется, библиотека *намеренно падает* с ошибкой `EMULATOR`, и снимается это только флагом подавления с формулировкой «suppress with extreme caution».
Причина — vsync-пейсинг и путь композиции эмулятора не соответствуют реальному `SurfaceFlinger`.

Что нельзя измерить без физического устройства:

* `frameOverrunMs` в осмысленном виде и классификацию джанка;
* тепловой троттлинг — а он важнее всего именно на большом документе;
* поведение реального IME: автодополнение системной клавиатуры и пакетные правки дают паттерн, который синтетические нажатия не воспроизводят.

На эмуляторе допустим только уровень A и сравнение «до и после» на неизменной конфигурации.
Абсолютные числа оттуда в критерии приёмки не переносятся.

*Для `T-010` нужен физический телефон*, желательно два: бюджетный и типовой, оба на Android 12 и выше — иначе ключевая метрика недоступна.

== Что осталось непроверенным

* Собственно предел: сколько строк выдерживает поле на нашем корпусе. Ни одного публичного числа не существует.
* Работает ли ограничение стилей видимой областью так, как ожидается, с текущей реализацией `OutputTransformation`.
* Появившийся в августе rich text API (`TextFieldBuffer.addStyle` со `SpanStyle`, `getSpanStyles`) — не изучен, может оказаться более прямым путём для подсветки.

== Что предлагается сделать до кода редактора

Собрать одноэкранный стенд: `BasicTextField` с `TextFieldState` и заглушкой `OutputTransformation`, которая ставит стили на весь документ.
Прогнать на нём уровень B — до того, как архитектура застынет.
Публичного числа не существует; единственный способ узнать свой предел — измерить его на своём корпусе.
