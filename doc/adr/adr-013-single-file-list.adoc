== Контекст

Владелец решил 2026-08-18: корень приложения — экран репозитория по раскладке 1a, *список один*, источник переключается из меню, Git-действия появляются только когда источник — клон.
Решение задаёт «что», но не говорит, каким кодом это получить, а сегодня список файлов в приложении заведён дважды.

Первый — на экране репозитория: `RepositoryScreenState.Ready.files`, рекурсивный обход рабочей копии, строка с меткой статуса (`M`/`A`/`D`/`?`), счётчиком диффа и временем правки, чипы-фильтры `ИЗМЕНЁННЫЕ` / `ВСЕ ФАЙЛЫ` / `НЕДАВНИЕ`.
Второй — внутри экрана редактора: `EditorDocument.Browsing` с `.adoc`-документами корня SAF-папки, плюс состояния `NoFolder` и `FolderFailed`.

Журнал фичи 007 уже назвал это «двумя понятиями файлов» и запретил использовать `listDocuments` моста как выборщик файлов репозитория (`progress.adoc:130`).
Пока экраны жили порознь, раздвоение было терпимо; после того как список становится корнем приложения, оно превращается в противоречие с решением владельца.

Обе половины закрыты требованиями и тестами чужих фич, поэтому цена любого варианта — не «сколько написать», а «чью спеку править».

== Решение

Остаётся один список — корневой, поверх абстракции источника.
Экран редактора становится «только документом»: состояния `NoFolder`, `FolderFailed` и `Browsing` уходят из `EditorScreenModel`, а вход в документ идёт с корня.

Источник даёт корню три вещи: перечень файлов, необязательный Git-статус и необязательный набор Git-действий.
Клон отдаёт всё три, папка SAF — только первое, и из этого автоматически следует правило видимости `FR-13`, а не из условий в вёрстке.

Спека фичи 005 правится вместе с реализацией: `FR-9`, `FR-21`, `FR-22` переформулируются под новый корень, кейсы `TC-20`, `TC-21`, `TC-22` переписываются.
Это отступление от чужой аналитики, и оно делается правкой аналитики, а не молча.

== Альтернативы

* *Оставить оба списка*: корень строится отдельно, редактор сохраняет свои состояния как запасной путь.
Отвергнут: два списка расходятся при первой же правке — разная сортировка, разные пустые состояния, разные правила фильтра, — и «список один» нарушается де-факто.
Спека 005 при этом остаётся правдой на бумаге и ложью на экране, что запрещено правилом «молчаливое расхождение кода и спеки».
* *Собирать корень из двух разных экранов*: `RepositoryScreen` при источнике-клоне, `Browsing` редактора при источнике-папке.
Отвергнут: пользователь видит два визуально разных списка в зависимости от источника — прямое нарушение решения владельца.
Дешевле всех по коду и дороже всех по продукту.
* *Обобщить в обратную сторону* — сделать корнем список редактора, а Git-части подмешивать.
Отвергнут: список редактора беднее (только `.adoc` корня папки, без статусов, без фильтров, без времени правки), и обобщение свелось бы к переписыванию его до состояния `RepositoryScreen` — та же работа, но с потерей закрытых тестов экрана «01».

== Последствия

Плюсы::
Одно понятие списка: одна вёрстка строки, один набор фильтров, одни пустые состояния.
Правило «Git-действия только у клона» выражено типом источника, а не условиями в вёрстке, поэтому не может разъехаться.
Экран редактора становится проще ровно на те состояния, которые ему не принадлежали: вкладки и так показываются только при открытом документе (`FR-22` фичи 005), то есть модель уже жила с этим противоречием.

Минусы и плата::
Правка чужой закрытой фичи: спека и тесты 005 переписываются, работа — слайс-полтора сверх врезки.
`EditorScreenModel.start(liftHeldSource)` и флаг `viewingList` теряют смысл в нынешнем виде и переезжают в навигатор — риск задеть уже закрытое поведение «назад» (`FR-21` фичи 005), поэтому его кейсы гоняются до и после.
Список папки SAF получает колонки, которых у него нет (статус, счётчик диффа): они опускаются, и это видимое отличие строк при одинаковой вёрстке — названное, а не случайное.

Что теперь придётся поддерживать::
Абстракцию источника: каждый новый источник (например, клон, открытый через `DocumentsProvider`) реализует её целиком, включая «Git-частей нет».
Требования 005, зависящие от списка, живут теперь в двух документах — в 005 остаётся документ, в 009 переезжает список; перекрёстные ссылки обязаны это отражать.
