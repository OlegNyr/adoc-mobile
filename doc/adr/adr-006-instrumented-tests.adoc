== Контекст

Четыре хвоста в трёх фичах упёрлись в один вопрос: часть тестов не исполнима в `commonTest`.

* `engine`-кейсы рендера (`TC-1`…`TC-4`, `TC-6` фичи 003) — нужен живой QuickJS с бандлом.
* Прогон корпуса сверки на устройстве (`T-037`) — нужен вывод движка с реального ARM.
* Бенчмарк подсветки (`T-024`) и перф-кейсы — числа с x86 не переносятся на телефон, что уже показали замеры: JVM-проба давала 670 мс там, где телефон дал 414.
* Группировка непрерывного ввода (`TC-10`, `TC-11` фичи 004) — слияние операций отмены записывает только сессия ввода, из `commonTest` это невоспроизводимо в принципе.

== Решение

*Инструментальный прогон на устройстве* (`androidInstrumentedTest`), отдельной задачей сборки, не входящей в `check`.

Обычный `check` остаётся быстрым и не требует устройства; инструментальный прогон гоняется с подключённым телефоном — перед закрытием слайсов, которым он нужен, и на приёмке.

== Рассмотренные альтернативы

JVM-таргет в `shared`::
`quickjs-kt` есть и для JVM — движковые тесты шли бы на каждом `check`.
Отклонено: числа с x86 не переносятся (расхождение уже наблюдалось), композицию это не решает, а новый таргет — заметная правка сборки ради половины задачи.

Оставить ручными::
Отклонено: регрессии ловились бы только памятью, против духа проекта, где каждый страж автоматический.

== Последствия

* В `shared` включается инструментальный таргет (в KMP-плагине AGP он, как и всё остальное, выключен по умолчанию — см. ловушки в `CLAUDE.md`).
* Перф-пороги (`TC-34`…`TC-36` подсветки, `TC-15`/`TC-16` превью) получают исполняемый дом; числа в критериях приёмки — только с устройства, это правило уже записано в разведке.
* Прогон корпуса на устройстве становится тестом, а не разовой процедурой: три исхода (новое расхождение / известное / известное исчезло) — требование `ADR-005`.
* CI без устройства инструментальный прогон не исполняет; его место — локальный прогон на приёмке слайса. Ферма устройств — решение за пределами MVP.
