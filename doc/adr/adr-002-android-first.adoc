== Контекст

Видение строит продукт на двух платформах, и один из критериев успеха MVP — «одна кодовая база собирается на обе платформы, доля платформенного кода ≤ 20 %».

Разработка ведётся на Windows.
Kotlin/Native для iOS требует macOS и Xcode: это ограничение тулчейна, а не настройка проекта, обойти его на Windows нельзя.
Mac недоступен.

Значит, iOS-половина плана — `T-012` (прототип рендера через `JSContext`), `T-032` (платформенная реализация рендера), `T-077` (libgit2 через `cinterop`) — локально неисполнима, а критерий MVP про две платформы непроверяем.

== Решение

Идём Android-first.
В каркасе заводим общий модуль и Android-приложение; iOS-таргет не добавляем, пока не появится macOS.

Архитектура при этом сохраняется двухплатформенной:

* швы `expect`/`actual` для рендера и превью объявляются сразу, с `expect`-объявлением в общем коде и единственной пока реализацией под Android;
* общий код не опирается на JVM-специфику — ни `java.*`, ни JVM-only библиотек в `commonMain`;
* решения, у которых нет iOS-аналога, помечаются в аналитике как незакрытый риск, а не молча принимаются.

Цель — чтобы добавление iOS-таргета было работой по написанию `actual`-реализаций, а не переделкой общего кода.

== Альтернативы

* *Оба таргета сразу, iOS собирается на macOS-раннере в CI* — отвергнут для этого этапа.
Сборка проходит, но обратная связь измеряется минутами вместо секунд, а отладка Kotlin/Native ведётся вслепую по логам.
На стадии, где ещё нет ни строчки кода, цена такого цикла выше пользы.
Вариант остаётся первым кандидатом на возврат, когда общий код стабилизируется.
* *Купить или арендовать Mac* — не отвергнут, а отложен: решение об этом принимается отдельно и переводит проект обратно на исходный план.

== Последствия

Плюсы:: цикл разработки быстрый; вся ранняя работа идёт по потокам 1–5 без простоя; риск `T-010` (производительность текстфилда) проверяется на реальном устройстве уже сейчас.

Минусы и плата:: критерий MVP «собирается на обе платформы» до появления macOS не проверяется — это записанное отступление от видения, а не забытый пункт.
Расхождения с iOS будут вскрываться позже и дороже: `JSContext` ведёт себя не так, как headless-движок на Android, а текстовый ввод Compose на iOS — самая чувствительная область по самому же видению.

Что придётся поддерживать:: дисциплину общего кода без JVM-зависимостей — без компилятора, который это проверит, пока iOS-таргет не заведён.
