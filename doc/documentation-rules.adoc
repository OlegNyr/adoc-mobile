[.lead]
Вся документация проекта ведётся в AsciiDoc.
Правила обязательны для людей и для агентов: новый документ создаётся сразу по ним, существующий приводится к ним при правке.

toc::[]

== Формат

. *Только AsciiDoc.* Расширение `.adoc`, кодировка UTF-8 без BOM.
Markdown-файлов в документации проекта не заводим — ни для черновиков, ни «на время».
. *Конвертация вместо сосуществования.* Если документ пришёл в Markdown, он переводится в `.adoc`, а исходный `.md` удаляется: двух версий одного текста быть не должно.
. Исключения — ровно два, и расширять их список нельзя без явного решения:
+
--
Определения инструментов:: `CLAUDE.md` в корне и `SKILL.md` с сопутствующими файлами `reference/` в `.claude/skills/` — формат задан инструментом, не нами. На то, что эти файлы *порождают*, исключение не распространяется: шаблоны скиллов переписаны в `.adoc`, и артефакты фичи в `doc/features/` создаются в AsciiDoc.
Ввозные артефакты:: файлы, пришедшие из внешних бандлов вместе с их содержимым (например `doc/design/README.md` из дизайн-хэндоффа). Они остаются в исходном виде как свидетельство источника; собственных правок в них не делаем — нужное переносим в наши `.adoc`.
--

== Язык и стиль

* Язык документации — русский.
Идентификаторы, имена API, пути, команды и названия технологий остаются латиницей и в моноширинном начертании: `TextFieldState`, `commonMain`, `doc/design/`.
* Одна мысль — одна строка.
Абзац набирается несколькими строками, каждая из которых заканчивается на границе предложения: так дифф показывает изменённое предложение, а не переформатированный абзац.
* Пишем утверждениями о продукте, а не о процессе: «превью строится Asciidoctor», а не «мы решили, что, наверное, будем строить».
* Решение живёт в одном документе. Остальные ссылаются на него через `xref:`, а не пересказывают: пересказ рассинхронизируется первым.

== Структура каталога

[source,text]
----
doc/
├── README.adoc                  карта документации
├── documentation-rules.adoc     этот файл
├── asciidoc-editor-vision.adoc  продуктовое видение
├── user-stories.adoc            пользовательские истории
└── design/
    ├── design.adoc              описание дизайна
    ├── *.png                    снимки экранов
    ├── README.md                ввозной артефакт бандла
    └── project/                 исходный дизайн-хэндофф (не редактируется)
----

* Верхний уровень `doc/` — документы о продукте.
* `doc/design/` — всё, что касается внешнего вида: описание, снимки экранов, исходный бандл.
* `doc/design/project/` — вход из внешнего инструмента. Читаем, не правим: при следующем экспорте правки затрёт.
* Имя файла — латиницей, в нижнем регистре, через дефис.

== Шапка документа

Каждый `.adoc` начинается одинаково:

[source,asciidoc]
----
= Заголовок документа
:toc: macro
:toc-title: Содержание
:sectnums:
:sectanchors:
:status: черновик | на ревью | действует
:revdate: ГГГГ-ММ-ДД
:icons: font

[.lead]
Одно-два предложения: о чём документ и чем он не является.

toc::[]
----

* `:revdate:` — только ISO-формат, обновляется при значимой правке (новый раздел, изменённое решение), но не при опечатке.
* `:status:` — состояние документа, а не продукта.
* Оглавление ставится через `toc::[]` после вводного абзаца, чтобы вводный абзац был виден до содержания.
* Заголовок первого уровня (`=`) в документе один; разделы начинаются с `==`.

== Разметка

Списки определений:: для пар «термин — пояснение». Читается лучше таблицы из двух колонок и не ломается на узком экране.

Таблицы:: только с явными `cols` и `options="header"`. Таблица уместна, когда сравниваются три и более сущностей по одинаковым признакам; для двух колонок берём список определений.

Блоки кода:: с указанием языка — `[source,kotlin]`, `[source,asciidoc]`. Для схем, деревьев и вывода команд — `[source,text]`.

Врезки:: `NOTE`, `IMPORTANT`, `WARNING` — по делу. Врезка, которую можно удалить без потери смысла, удаляется.

Изображения::
Лежат рядом с документом, вставляются как `image::файл.png[описание, ширина]`.
Описание обязательно: по нему ищут нужный снимок и оно остаётся вместо картинки, если файл не найден.

Диаграммы::
Пишутся текстом в блоке `[plantuml]` или `[mermaid]`, а не вставляются картинкой.
Это тот же путь через Kroki, который поддерживает сам продукт, — документация проверяет продукт на себе.

== Ссылки и якоря

* Между документами — `xref:user-stories.adoc[Пользовательские истории]`, путь относительный.
Из `doc/design/` наверх — `xref:../asciidoc-editor-vision.adoc[…]`.
* Ссылка на конкретную историю — через её якорь: `xref:../user-stories.adoc#US-E5-04[US-E5-04]`.
* Абсолютные пути (`D:\IdeaProjects\…`, `file://`) в документации запрещены: они верны только на одной машине.
* Идентификаторы историй (`US-E5-04`) неизменны.
Историю можно закрыть или переписать, но не перенумеровать: на неё уже ссылаются другие документы.

== Что где описывается

[cols="1,2,2", options="header"]
|===
| Документ | Отвечает на | Не содержит

| Видение
| Зачем продукт, что в скоупе, какая архитектура и почему, какие риски
| Пошаговых сценариев, вёрстки, размеров

| Пользовательские истории
| Кто что делает и как проверить, что готово
| Обоснований решений и технических деталей реализации

| Описание дизайна
| Как это выглядит: токены, компоненты, экраны
| Продуктовых обоснований и критериев приёмки
|===

Если факт хочется написать в двух документах — он принадлежит одному из них, а второй ставит `xref:`.

== Проверка

Сборка документации в проекте пока не настроена.
Если локально установлен Asciidoctor, документ перед фиксацией проверяется на отсутствие предупреждений:

[,bash]
----
asciidoctor --failure-level=WARN -o /dev/null doc/*.adoc doc/design/*.adoc
----

Отдельно смотрим, что не появилось: битых `xref:`, изображений без описания, ссылок на несуществующие якоря.
