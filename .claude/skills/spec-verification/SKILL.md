# Spec verification

Сверяет **спеку и код** в обе стороны и чинит расхождение — правкой документа или заведением
слайса, но не замалчиванием. Дополняет `feature-analysis` (та пишет спеку *до* кода).

Адаптировано из Tessl spec-driven-development tile (MIT).

## Когда запускать

- Слайс закрыт — перед записью в `progress.adoc`.
- Перед переводом фичи в `:status: done`.
- Спека выглядит устаревшей: `targets` указывают в никуда, `[@test]` на несуществующие файлы.
- Пользователь просит проверить соответствие кода спеке.

## Ход работы

### 1. Собрать зону сверки
Возьми `doc/features/NNN-<slug>/`. Источники истины по ролям: `analysis.adoc` (требования),
`spec/*.spec.adoc` (контракты подсистем), `plan.adoc` (что должно быть сделано), код по `targets`.

### 2. Проверить целостность ссылок (дёшево, делай первым)
- Каждый глоб `targets` матчит хотя бы один существующий файл.
- Каждый `[@test]` указывает на существующий файл теста; в нём есть тест с этим ID
  (имя/`@DisplayName` начинается с `TC-n`).
- Каждый `SL-n` в `progress.adoc` есть в реестре `plan.adoc`, и статусы не противоречат.
- Каждый Must-FR попадает хотя бы в один слайс.

### 3. Сверить требования с реализацией
Для каждого FR/NFR со статусом «сделано» найди в коде место, которое его реализует, и
подтверди поведение — **читая код, а не полагаясь на текст спеки**. Классифицируй:

| Тип дрейфа | Что значит | Что делать |
|---|---|---|
| **Не реализовано** | требование заявлено сделанным, кода нет | вернуть статус, завести слайс |
| **Реализовано иначе** | код делает не то, что написано | решить с owner: правим код или требование |
| **Реализовано сверх спеки** | в коде поведение, которого нет в требованиях | дописать FR или удалить код |
| **Тест не проверяет** | `[@test]` есть, но тест проверяет не то | переписать тест |
| **Мёртвое требование** | требование потеряло смысл | пометить `Won't` с причиной, не удалять молча |

### 4. Отчитаться
Список расхождений с типом, файлом и строкой, отсортированный по серьёзности. Ничего не
правь молча: правки требований и статусов — только после подтверждения владельцем
(правило **spec-before-code** в `feature-analysis/reference/rules.md`).

Починка ссылок и статусов (`[@test]`, `targets`, рассинхрон `plan.adoc`/`progress.adoc`) —
можно сразу, это техническая гигиена.

## Правила

- Спека и код равноправны как улики: расхождение — не всегда баг кода. Часто устарел документ.
- Не пиши «соответствует» без прочтения кода. Совпадение названий — не проверка.
- Границы (`plan.adoc` §5, 🚫 Never) проверяй отдельно: нарушение запрета — всегда находка
  высокой серьёзности, даже если функционально всё работает.
