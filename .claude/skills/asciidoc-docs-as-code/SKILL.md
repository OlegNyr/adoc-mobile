# AsciiDoc Docs-as-Code

Документация — это продукт со своей сборкой, тестами и релизами. Этот скилл
описывает, как делать её так, как делают зрелые опенсорс-проекты: исходники в
git, один источник → сайт + PDF + слайды, примеры кода включаются из
компилируемых файлов, вёрстка узнаваемая, а не дефолтная.

Ключевая идея, вокруг которой всё построено: **дефолтный вывод Asciidoctor
выглядит как научная статья 2003 года.** Именно поэтому большинство доков на
AsciiDoc выглядят одинаково-серо и именно поэтому уход от дефолта — самый
дешёвый способ получить «вау». Всё, что для этого нужно, лежит в
`assets/` этого скилла.

## Шаг 0. Выбери режим сборки

Не начинай писать `.adoc`, пока не понял, куда он поедет. Три реальных
сценария, всё остальное — их частные случаи:

| Признаки в задаче | Режим | Читать дальше |
| --- | --- | --- |
| Несколько репозиториев/компонентов, версионирование доки, «портал», навигация слева, поиск | **Antora** | `references/build-antora.md` |
| Один репозиторий, дока рядом с кодом, нужен HTML/PDF/слайды из Maven или Gradle | **Asciidoctor build** | `references/build-asciidoctor.md` |
| Итог должен оказаться в Confluence (Data Center/Cloud), корпоративный контур | **Confluence Publisher** | `references/confluence-publisher.md` |

Если неоднозначно — спроси одним вопросом, а не тремя. По умолчанию для
«сделай красивый сайт документации» бери **Antora**: она даёт версии,
навигацию и поиск из коробки, и это де-факто стандарт (docs.asciidoctor.org,
docs.spring.io, Camel, Neo4j, Vert.x собраны именно так).

Дальше по всем режимам общее: структура, правила письма, фирменный вид,
проверки.

## Шаг 1. Структура репозитория

Возьми Diátaxis — четыре типа текста, которые нельзя смешивать в одном файле.
Это то, что отличает читаемую доку от свалки:

- **tutorial** — «пройди со мной от нуля до работающего», гарантированный успех;
- **how-to** — «реши конкретную задачу», читатель уже в контексте;
- **reference** — сухое описание API/конфига, никаких повествований;
- **explanation** — «почему так», архитектура, компромиссы, ADR.

Канон дерева (Antora-вариант; для single-repo см. `build-asciidoctor.md`):

```
docs/
├── antora.yml
└── modules/
    └── ROOT/
        ├── nav.adoc                 навигация — один источник правды
        ├── pages/
        │   ├── index.adoc           лендинг с карточками
        │   ├── tutorial/…
        │   ├── how-to/…
        │   ├── reference/…
        │   └── explanation/…
        ├── partials/                переиспользуемые куски, не страницы
        ├── examples/                КОД, который включается в страницы
        ├── images/
        └── attachments/
docs/decisions/0001-*.adoc           ADR в формате MADR
CONTRIBUTING.adoc  README.adoc  .vale.ini  antora-playbook.yml
```

Правило, которое экономит недели: **страница ≠ файл-помойка**. Один заголовок
уровня `=` на файл, дальше `==`. Если файл перевалил за ~300 строк — это
признак, что внутри сидят два разных типа Diátaxis.

## Шаг 2. Пиши AsciiDoc, а не Markdown с другим синтаксисом

Смысл переезда на AsciiDoc — в возможностях, которых нет в Markdown. Если их
не использовать, переезд бессмыслен. Обязательный минимум в каждом проекте:

**Шапка документа с атрибутами.** Версии, пути и URL живут в одном месте и
подставляются по всему тексту:

```asciidoc
= Заголовок страницы
:description: Одно предложение для SEO и превью
:keywords: asciidoc, docs-as-code
:source-highlighter: highlight.js
:icons: font
:experimental:
:sectanchors:
:toc: macro
:spring-boot-version: 3.5.0
```

`:experimental:` включает `kbd:[Ctrl+C]`, `btn:[Сохранить]`, `menu:File[Save]`
— мелочь, которая мгновенно повышает воспринимаемое качество UI-инструкций.

**Включение живого кода по тегам — главная суперсила.** Примеры не копируются
в текст, а включаются из файла, который компилируется в CI:

```java
// tag::consumer[]
@KafkaListener(topics = "chat-events")
public void onEvent(ChatEvent event) { … }
// end::consumer[]
```

```asciidoc
[,java]
----
include::example$kafka/ChatConsumer.java[tag=consumer,indent=0]
----
```

Дока физически не может протухнуть: сломался пример — упала сборка. Это то,
что делают Spring и Quarkus, и это первое, что стоит внедрить.

**Callout-аннотации.** Разбор кода по номерам вместо пересказа под блоком:

````asciidoc
[,java]
----
var props = new HashMap<String, Object>();
props.put(BOOTSTRAP_SERVERS_CONFIG, brokers);  // <1>
props.put(GROUP_ID_CONFIG, "chat-worker");     // <2>
----
<1> Адреса брокеров берутся из `application.yml`, а не хардкодятся.
<2> Group id должен совпадать с именем деплоймента, иначе ребалансировка съест партиции.
````

**Ссылки только через `xref:`**, не через относительные пути к html. Antora и
Asciidoctor проверяют такие ссылки при сборке и ломают билд на битой ссылке.

**Условные блоки для single-source.** Одна ветка исходников на внутреннюю и
публичную версию:

```asciidoc
ifdef::internal[]
NOTE: Пароли сервисной учётки — в Vault, путь `secret/cc/prod`.
endif::[]
```

Полная выжимка синтаксиса, включая таблицы, списки определений, сноски и
блоки — в `references/syntax-power.adoc`.

## Шаг 3. Фирменный вид

Здесь скилл окупается. Семь приёмов, каждый из которых работает по
отдельности; вместе они дают вид, который не спутать с дефолтом.

1. **Тема.** Подключи `assets/theme/signature.css`: типографическая пара
   (гротеск для текста + моно для кода), цветной рельс у заголовков,
   аккуратные отступы, поддержка тёмной темы через `prefers-color-scheme`.
2. **Хиро-блок на лендинге** — крупный заголовок, подзаголовок, ряд бейджей
   версии/лицензии/сборки.
3. **Сетка карточек** вместо оглавления-списка на главной. В AsciiDoc это
   `[.cards]` над списком, остальное делает CSS.
4. **Табы** для Maven/Gradle, Java/Kotlin, curl/httpie — читатель не листает
   мимо чужого стека.
5. **Расширенные адмонишены** — помимо пяти встроенных добавь роли
   `[.admonition.security]`, `[.admonition.perf]`, `[.admonition.gotcha]`.
6. **Диаграммы из текста** через Kroki/PlantUML в едином палитровом стиле
   (`assets/plantuml/theme.puml`) — они диффятся в git и не разъезжаются с
   реальностью.
7. **Микро-интеракции**: кнопка «копировать» на блоках кода, якоря по ховеру,
   полоса прогресса чтения, переключатель темы. Всё в
   `assets/theme/docinfo-footer.html`, ванильный JS, без зависимостей.

Как именно подключать это в каждом из трёх режимов сборки и весь набор
CSS-ролей — в `references/visual-style.md`. Не изобретай свой CSS с нуля:
бери ассеты и меняй переменные в `:root`.

Ограничение, о котором легко забыть в корпоративном контуре: **никакого
внешнего CDN в проде документации.** Шрифты — системный стек, диаграммы
рендерятся на сборке (`:kroki-fetch-diagram:` или локальный PlantUML), JS
лежит в репозитории. Если ассеты тянутся из интернета, дока не соберётся за
периметром и не пройдёт ревью безопасности.

## Шаг 4. Диаграммы

Правило выбора: **текст, который компилируется в SVG, всегда лучше картинки.**

- PlantUML — последовательности, компоненты, C4 (через `!include` стандартной
  библиотеки C4-PlantUML);
- Mermaid — быстрые флоучарты, гантты;
- D2 — архитектурные схемы, где важна раскладка;
- draw.io — только когда нужен художественный контроль; тогда коммить `.drawio`
  рядом с экспортированным `.svg`.

Подробности, включая offline-рендеринг и общий стиль, — в
`references/diagrams.md`.

## Шаг 5. Проверки в CI

Дока без CI деградирует за квартал. Минимальный набор, который стоит завести
сразу:

- **сборка** — падает на битом `xref:`, отсутствующем `include::`, невалидном nav;
- **lychee** — битые внешние ссылки;
- **Vale** — стиль и терминология (словарь проекта, запрет «просто», «легко»,
  «очевидно», единообразие «Kafka», а не «кафка»);
- **компиляция примеров** — модуль `docs-examples` собирается обычным `mvn test`;
- **preview на PR** — артефакт сайта или деплой в ветку, чтобы ревьюер видел
  результат, а не диф разметки.

Готовые конфиги и workflow — в `references/oss-conventions.md`.

## Чеклист качества

Перед тем как отдать результат, пройдись по списку. Если пункт не выполнен —
это либо сознательный компромисс, о котором надо сказать, либо недоделка:

- [ ] Выбран и назван режим сборки; сборка воспроизводится одной командой.
- [ ] Каждая страница относится ровно к одному типу Diátaxis.
- [ ] Ни одного скопированного примера кода — только `include` с тегами.
- [ ] Все внутренние ссылки — `xref:`, сборка падает на битой.
- [ ] Версии и пути вынесены в атрибуты, а не размазаны по тексту.
- [ ] Подключена тема; вид отличается от дефолтного Asciidoctor.
- [ ] Все схемы — текстовые исходники в репозитории.
- [ ] Нет обращений к внешним CDN на этапе рендеринга.
- [ ] Есть `README.adoc`, `CONTRIBUTING.adoc` и хотя бы один ADR.
- [ ] В CI есть сборка + проверка ссылок.

## Антипаттерны

- **`.adoc` как один гигантский файл** — теряется навигация, диффы
  нечитаемы, конфликты слияния на каждом PR.
- **Скриншоты UI вместо текста** — не ищутся, не переводятся, протухают за
  один релиз. Скриншот оправдан, только когда объясняет пространственное
  расположение.
- **Дока в отдельном репозитории от кода** — рассинхрон гарантирован. Держи
  рядом, публикуй отдельно (в Antora это ровно то, для чего нужен playbook).
- **Ручная нумерация разделов** — есть `:sectnums:`.
- **Копипаста конфигов между страницами** — есть `partial$`.
- **Правки прямо в Confluence** при живом Publisher-пайплайне — следующая
  публикация их снесёт.
