# Аналитика фич — регламент (feature-analysis)

Проработка фичи **до** кода: vision → research → requirements → use cases → test cases →
design → декомпозиция.
Для backend-сервисов на Java / Spring Boot. Основа: ISO/IEC/IEEE 29148, use cases
по Cockburn, BDD Given-When-Then, MoSCoW, ADR по Nygard.

Запуск: `/feature-analysis <идея>`. Документ пишется в `doc/features/NNN-<slug>/analysis.adoc`
целевого проекта; шаблоны — в директории скилла (`templates/`).

## Адаптивная строгость (tier)

| Tier | Когда | Фазы |
|------|-------|------|
| **S** — твик/фикс | поведение очевидно | Ф0 Vision (кратко) + Ф4 Acceptance |
| **M** — обычная фича | новая возможность в слое | Ф0 + Ф-R (кратко) + Ф1 + Ф2 (чеклистом) + Ф3 (кратко) + Ф4 + §5 якорями + Ф5.5 + матрица; ADR при развилке |
| **L** — крупная фича | многослойная / влияет на архитектуру / меняет контракт | все фазы Ф0–Ф5.5, включая Ф-R и Ф-S при неизвестном API + под-спеки подсистем + ADR + полная матрица |

Ф-R обязательна, когда фича опирается на незнакомый API фреймворка или библиотеки, на
контракт внешней системы или на поведение эталона; для S её заменяет беглая сверка по коду.

Адаптивная строгость — главная защита от того, на чём спотыкаются Kiro и spec-kit:
мелкий баг не должен порождать четыре истории с шестнадцатью критериями и восемь файлов.

## Фазы и гейты

```
Ф0 VISION (draft) → понятно ЗАЧЕМ и для КОГО, без «как»
Ф-R RESEARCH      → эталон / платформа / наш код / ограничения; каждое утверждение с источником
Ф-S SPIKE         → (при необходимости) гипотеза проверена фактом, прототип выброшен
Ф0′ VISION (final)→ vision переписан с учётом найденных ограничений и не-целей
Ф1 REQUIREMENTS   → проверяемо и атомарно (INVEST); NFR-чеклист backend-сервиса пройден
Ф2 SPRING INTEG.  → названы поверхности, регистрация бинов, внешние зависимости, флаги
Ф3 USE CASES      → каждый FR покрыт ≥1 UC; учтён актор system-event
Ф4 TEST CASES     → каждый шаг UC и каждый NFR имеет проверку (auto/manual)
Ф5 DESIGN         → Design anchors + ADR: «как» предсказуемо для хендоффа
Ф5.5 DECOMPOSITION→ подсистемы → этапы (rolling wave) → вертикальные слайсы; boundaries
Ф6 CLOSING LOOP   → на каждый слайс: реализация → ревью → починка → ревью → документация
                    → форматирование (IDEA) → коммит с ID слайса   (см. closing-loop.md)
```

Ф6 повторяется столько раз, сколько слайсов в реестре, и внутри себя циклична: ревью и
починка чередуются до чистого раунда, предел — 3 раунда. Слайс без пройденного цикла не
переводится в ✅.

Не переходишь к следующей фазе, пока не закрыт выход текущей. Направляй к профильным
скиллам проекта, если они есть: `spring-boot-validation`, `spring-boot-observability`,
`spec-verification`, `maven-source`, `jar-decompile`.

## Структура каталога (в целевом проекте)

```
doc/features/
  NNN-<slug>/
    research.adoc              # разведка до требований: эталон, платформа, наш код, ограничения (M/L)
    analysis.adoc              # что и зачем — стабилен после approved
    plan.adoc                  # подсистемы, этапы, реестр слайсов, boundaries — живой (M/L)
    progress.adoc              # журнал закрытых слайсов — только постфактум (M/L)
    spec/<подсистема>.spec.adoc # контракт подсистемы, targets + [@test] (L, при ≥3 подсистемах)
    adr/adr-001-<slug>.adoc
```

Роли не смешивать. Журнал работ в `analysis.adoc` — самая частая деформация: секция
«Открытые вопросы» превращается в летопись, документ распухает и перестаёт читаться.

## ID-схема (трассируемость)

- `FR-n` / `NFR-n` — требования · `UC-n` — сценарии · `TC-n` — тесты · `ADR-n` — решения
  · `SL-n` — слайсы · `S-X` — подсистемы · `E-n` — этапы.
- UC ссылается на FR; TC — на UC/FR/NFR; SL — на FR/NFR/TC, которые закрывает.
- Коммиты/PR: `feat(NNN): … — SL-4, closes FR-2, TC-3`.
- Имя теста / `@DisplayName` начинается с ID: `TC-3: …`.

## Статусы

Документ: `draft` → `approved` (гейты Ф0–Ф5.5 закрыты) → `in-progress` → `done`.
Слайс в реестре: ⬜ не начат · 🔄 в работе · ✅ закрыт · ⏸️ отложен · ❌ отменён.

## Правила

Обязательные — в `rules.md`: **spec-before-code**, **one-question-at-a-time**,
**spec-format-compliance**. Цикл закрытия слайса — в `closing-loop.md`. Сверка кода со
спекой после реализации — скилл `spec-verification` (входит в цикл как отдельный ревьюер).

## Проектный overlay

Скилл рассчитан на Java / Spring Boot, но обезличен. Конкретные имена (стек и его версии,
слои, стартеры, схема БД, доменный словарь, инварианты) — из **CLAUDE.md и `.claude/rules/`
целевого проекта**. Если проект задаёт свой NFR-чеклист — применять поверх дефолтного.
