# Правила аналитики (обязательные)

Адаптировано из Tessl spec-driven-development tile (MIT). Правила действуют на всём
протяжении работы со спекой, а не только внутри `/feature-analysis`.

## 1. spec-before-code (обязательное)

**Ни строчки реализации, пока требования не зафиксированы и не одобрены владельцем.**

- Запрос «сделай фичу» без спеки → сначала спека, потом код. Скажи об этом прямо и предложи
  запустить аналитику, не начинай писать «пока набросок».
- Одобрение — явное: `:status: approved` в `analysis.adoc`. «Ок, звучит хорошо» в чате — не одобрение
  спеки, если после этого файл не обновлён.
- Реализация ведётся **против одобренного** текста. Разошлись — правь `analysis.adoc`, а не молча код.

**Исключения (спека не нужна):** очевидная опечатка, форматирование, правка комментария,
откат последнего изменения, разовый диагностический скрипт. Для всего, что меняет
наблюдаемое поведение, — нужна хотя бы tier S.

**Почему.** Без этого правила спека превращается в отчёт о уже написанном коде и теряет
единственную свою функцию — быть предметом договорённости *до* работы.

## 2. one-question-at-a-time (обязательное)

**Одна развилка за раз. Задал — жди ответа.**

- Вопрос должен быть конкретным и закрывающим: «Возвращать 404 или пустой список?» вместо
  «Как должен вести себя API?».
- Не вываливай список из десяти вопросов: владелец ответит на первые два и устанет,
  а остальные ты допридумаешь сам — это и есть источник выдуманных требований.
- Приоритет: сначала вопрос, ответ на который меняет больше всего последующих решений.
- **Про `AskUserQuestion`:** несколько вопросов в одном вызове допустимы, только если они
  строго независимы (ответ на один не меняет формулировку другого) и их не больше 2–3.
  Зависимые развилки — строго по одной, последовательно.
- Если ответ очевиден из CLAUDE.md, кода или уже принятых ADR — не спрашивай, предложи
  и попроси подтвердить одной строкой.

**Почему.** Каскад вопросов даёт иллюзию согласования: отвечают на первый, а остальные
закрываются догадками агента, которые потом всплывают как «я такого не просил».

## 3. spec-format-compliance (обязательное в этом проекте)

- Файлы фичи — только по ролям: `analysis.adoc` (что/зачем), `plan.adoc` (как режем),
  `progress.adoc` (что сделано), `spec/*.spec.adoc` (контракты подсистем, tier L), `adr/` (решения).
- Атрибуты документа в шапке обязательны и заполнены реальными значениями — никаких
  `<owner>` и `ГГГГ-ММ-ДД` в утверждённом документе.
- Формат файлов фичи — AsciiDoc (`.adoc`), как и вся документация проекта. Шаблоны в
  `templates/` — тоже `.adoc`; Markdown-файлов в `doc/features/` не заводим.
- `targets` указывает на существующие пути/глобы; `[@test]` — на существующий файл теста
  или явное `(нет)` с заведённым слайсом.
- Требование формулируется как проверяемое (ДОЛЖНА / МОЖЕТ / НЕ ДОЛЖНА), без «удобно»,
  «быстро», «интуитивно» без числа или наблюдаемого признака.
- ID сквозные и не переиспользуются: удалённый `FR-7` не возвращается под другим смыслом.
