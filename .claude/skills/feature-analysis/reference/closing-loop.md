# Цикл закрытия слайса (Ф6)

Регламент того, что происходит **после** написания кода слайса и **до** того, как слайс
считается закрытым. Карта цикла — в `SKILL.md`, §«Ф6. Закрытие слайса»; здесь детали.

Цикл обязателен для каждого слайса из реестра `plan.adoc`. Слайс без пройденного цикла
остаётся 🔄 «в работе», даже если код написан и тесты зелёные.

```
Ф6.1 Реализация ──► Ф6.2 Ревью ──► Ф6.3 Починка ──► Ф6.4 Ревью (повтор)
                         ▲                                    │
                         └────────── находки есть ────────────┘
                                                              │ чисто
                                    Ф6.5 Документация ◄───────┘
                                              │
                                    Ф6.6 Форматирование (IDEA)
                                              │
                                    Ф6.7 Коммит
```

---

## Ф6.1 Реализация

TDD по `rules.md` и `contribution.md` §4: падающий тест → минимальный код → рефакторинг.
Выход из фазы: все `TC-*`, перечисленные в слайсе, покрыты тестами и прогон зелёный.

Прогон — через wrapper проекта (команды — в `CLAUDE.md` целевого проекта). Красный прогон
в ревью не отдаём: ревьюеры потратят раунд на то, что видно из вывода тестов.

---

## Ф6.2 Ревью (раунд)

Две группы проверяющих, **запускаются параллельно** — все вызовы одним сообщением.

### Субагенты по линзам

Каждая линза — отдельный субагент **только на чтение** (`Explore` либо `general-purpose`
с явным запретом правок в промпте). Правит код всегда основной агент в Ф6.3: ревьюер,
который сам чинит, перестаёт быть независимым и прячет находки в диффе.

| Линза | Что проверяет | Чем подкрепляет находку |
|-------|---------------|-------------------------|
| **L-spec** | Код делает ровно то, что записано в слайсе: «Закрывает» из `plan.adoc`, соответствующие `FR-*`/`TC-*`/`UC-*` из `analysis.adoc`. Недоделанное и лишнее — одинаково находка | ID требования / шаг UC |
| **L-rules** | `.claude/rules/codestyle.md` (отступы, длина строки, порядок импортов и модификаторов, `TODO:`, `L`-суффикс), `contribution.md` (слои, package-by-feature, Lombok, DI через конструктор, автоконфиги), `ubiquitous-language.md` (нейминг артефактов) | пункт правила |
| **L-correctness** | Дефекты: граничные случаи, `null`, конкурентность, утечки ресурсов, обработка ошибок; тесты проверяют **наблюдаемое поведение**, а не факт вызова мока | сценарий воспроизведения |

Промпт каждому субагенту обязан содержать: путь к `analysis.adoc` и `plan.adoc`, ID слайса,
список изменённых файлов (`git diff --name-only`), формулировку линзы и требование
**не править файлы**.

### Проектные скиллы

Запускаются в том же раунде, когда применимы:

| Скилл | Когда обязателен |
|-------|------------------|
| `spec-verification` | всегда, если у фичи есть `spec/*.spec.adoc` или слайс менял поведение, описанное в `analysis.adoc` |
| `security-review` | слайс касается внешней поверхности, аутентификации, ПДн, аудита, файлов или конфигурации доступа |
| `simplify` | по усмотрению: когда слайс оставил дублирование или разросшийся класс |

### Что считается находкой

Находка принимается, только если у неё есть **файл:строка**, утверждение о дефекте и
подтверждение — пункт правила, ID требования или воспроизводимый сценарий. Замечание
«так красивее» без ссылки отклоняется; вкусовые правки в цикле закрытия не делаются.

Отчёты субагентов пользователю не показываются — релеить итог: сколько находок, какие
приняты, какие отклонены и почему.

---

## Ф6.3 Починка

- Чинить **все принятые** находки в рамках текущего слайса.
- Каждая починка дефекта закрывается тестом: существующим `TC-*` либо новым регрессным.
  Починка без теста означает, что тот же дефект вернётся.
- Отклонённую находку нельзя проигнорировать молча — она записывается в `progress.adoc`,
  поле «Ревью», с одной строкой обоснования.
- Находка, выходящая за рамки слайса, **не чинится здесь**: заводится новый слайс в
  `plan.adoc` (или запись в `analysis.adoc` §7) и упоминается в `progress.adoc`. Расширять слайс
  по ходу ревью — верный способ его не закрыть.

---

## Ф6.4 Ревью, повторный раунд

- Гоняются линзы, у которых **были находки** в предыдущем раунде, плюс всегда — прогон тестов.
- Если починка задела чужую зону (например, правка ради `L-correctness` изменила публичный
  API) — линзу этой зоны тоже перезапустить.
- **Условие выхода:** раунд без принятых находок.
- **Предел — 3 раунда.** Если после третьего находки остаются, цикл останавливается:
  слайс не закрывается, остаток режется на новый слайс в `plan.adoc`, в `progress.adoc`
  фиксируется, что именно осталось. Бесконечный цикл ревью — это нарезка, а не качество.

---

## Ф6.5 Документация

Обновляется до форматирования и коммита, чтобы попасть в тот же коммит:

1. `progress.adoc` — запись по шаблону: сделано, отступления, осталось незакрытым, ревью.
2. `plan.adoc` — статус слайса в реестре (✅), при необходимости — новые слайсы из Ф6.3.
3. `analysis.adoc` — колонка «Статус» матрицы §6. Если реализация разошлась с требованием,
   правится **сам текст требования**, а в `progress.adoc` остаётся ссылка на правку.
4. `adr/` — если в ходе слайса принято решение, меняющее ранее записанное.
5. Javadoc публичного API и проектная документация (`doc/**`), если слайс изменил
   поведение, которое там описано. Ссылки и якоря документов не ломать.

---

## Ф6.6 Стиль

Сверить изменённые файлы с `codestyle.md` **глазами**: отступы, длина строки, порядок и
группировка импортов, пустые строки в теле класса, Javadoc публичного API.

**Автоформатирование через IDE не запускать.** Решение владельца от 2026-08-03: настройки
code style в IDE расходятся с `codestyle.md` (IDEA ставит 4 пробела и разделяет группы
импортов пустыми строками), и `reformat_file` молча переписывает уже закоммиченный код.
Проверка проблем (`get_file_problems`) допустима — она ничего не меняет; правка кода
инспекциями — нет.

Диагностика IDE полезна как *источник находок для ревью*, но не как шаг, который сам правит
файлы. Если в проекте появится Spotless/Checkstyle с конфигом из репозитория — форматирование
вернётся сюда уже в виде команды сборки, а не действия IDE.

---

## Ф6.7 Коммит

Коммит делается **автоматически**, без отдельного вопроса, когда выполнено всё:
тесты зелёные · раунд ревью чистый · документация обновлена · форматирование пройдено.

- **Один слайс — один коммит.** Индексируются только файлы слайса; `git add -A` вслепую —
  запрещено (в рабочем дереве бывает чужое).
- Сообщение содержит ID: `feat(NNN): <что стало возможно> — SL-4, closes FR-2, TC-3`.
  Тип по смыслу: `feat` / `fix` / `docs` / `test` / `refactor` / `chore`.
- Трейлер `Co-Authored-By` — по правилу среды исполнения.
- Если текущая ветка — дефолтная (`master`/`main`), сначала завести ветку под фичу.
- **Push и PR не делаются** без явной просьбы пользователя.
- Если что-то из условий не выполнено — коммита нет; сказать, что именно не закрыто.

---

## Границы цикла

- ✅ **Always** — прогонять цикл целиком на каждом слайсе; ревьюеры только читают; каждая
  починка покрыта тестом; статус слайса обновляется в `plan.adoc`.
- ⚠️ **Ask first** — расширение рамок слайса по итогам ревью; правка требования в
  `analysis.adoc`; отказ от целой линзы ревью.
- 🚫 **Never** — коммит при красных тестах или непройденном ревью; молчаливое игнорирование
  находки; починка «заодно» чужого кода вне слайса; push/PR без просьбы;
  переформатирование файлов, которых слайс не касался.
